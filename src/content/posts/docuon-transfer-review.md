DocuON 포털에서 문서 이관을 신청하면 “문서가 이관되었습니다”라는 안내가 뜬다. 같은 요청에 응답하는 Java 컨트롤러의 문구에는 **신청**이라는 단어가 하나 더 있다. “문서 이관 신청이 완료되었습니다.” 이 차이가 궁금해서 버튼 다음에 바뀌는 데이터를 따라가 봤다.

## 문서 한 건에 첨부 파일이 두 개라면

가상의 ‘보관 기록’ 한 건에 본문 PDF와 별지 PDF가 하나씩 붙어 있다고 하자. 포털에서 ‘이관신청’을 열면 신청 대상 문서는 이미 정해져 있다. 사용자는 목적 보관소를 확인하고 사유를 입력한다. `TransferAppModal.vue`는 문서 ID, 보관소, 사유, 신청일을 Pinia 액션에 넘긴다. 응답이 성공하면 부모의 문서 상세 화면이 다시 조회하도록 이벤트를 보낸다.

서버의 `requestTransferDocuments`는 해당 문서의 파일 수를 조회하고 신청 이력 한 건을 만든다. 이어서 각 파일의 식별자를 같은 신청에 연결하고 문서의 서비스 상태를 ‘이관 처리 중’으로 바꾼다. 신청 생성, 파일 연결, 상태 변경은 같은 트랜잭션에 들어 있다.

| 예시에서 세는 대상 | 수량 | 무엇을 나타내나 |
| --- | ---: | --- |
| 신청 | 1건 | 운영자가 승인하거나 반려할 업무 한 건 |
| 문서 | 1건 | 포털에서 선택한 ‘보관 기록’ |
| 상세 이력 | 2건 | 이 신청에 포함된 본문과 별지 각각의 연결 |

본문과 별지를 각각 승인해야 할까? 운영자는 하나의 신청을 심사한다. 그 결정에 어떤 파일이 포함되는지는 상세 이력에서 확인한다. 접수 직후 안내를 ‘이관 신청을 접수했습니다’라고 쓰면 이 시점에 일어난 일을 정확히 전달할 수 있다.

## 관리자가 승인 버튼을 누른 뒤

관리자 화면 `ApprovalDetail.vue`는 주소의 신청 ID로 신청 정보와 대상 목록을 차례로 읽는다. 앞의 데이터에는 현재 심사 상태와 신청 사유가 있고, 뒤의 데이터에는 심사 대상을 확인할 행들이 있다. 승인·반려 버튼은 신청이 접수 상태일 때 활성화된다.

승인을 누르면 사유 입력창이 열린다. 운영자가 사유를 입력하고 다시 확인해야 모달이 신청 ID와 사유를 부모 화면으로 돌려준다. 최종 확인에서 취소하면 승인 API 호출까지 가지 않는다. 앞서 포털에서 접수한 신청은 그대로다.

확인하면 `processApproval`이 신청 이력에 승인 결과와 사유를 기록하고 무결성 기록을 위한 이벤트를 등록한다. 이 메서드에서 확인되는 범위는 심사 기록까지다. 파일이 목적 보관소에 도착한 시점이나 수신 확인 절차는 이 호출만으로 정할 수 없다. 성공 응답을 받은 관리자 화면은 신청 정보와 대상 목록을 다시 읽고 ‘이관 승인 완료’를 안내한다. 이때 읽어 온 신청 상태가 가리키는 사건은 운영자가 심사를 마쳤다는 것이다.

## 반려라면 어떤 상태를 되돌려야 할까

위 예시에서 목적 보관소를 잘못 선택했다고 하자. 운영자가 사유를 적어 반려하면 `processRejection`은 두 곳을 바꾼다. 신청 이력에는 반려 결과와 사유를 남긴다. 이어 MyBatis가 이 신청 ID로 연결된 문서를 찾아 서비스 상태를 활성으로 되돌린다. 신청 내역을 열면 반려 사유를 읽을 수 있고, 문서 상세로 돌아가면 이관 처리 중이었던 문서가 다시 활성 상태가 된다.

| 사용자 동작 | 신청 쪽에서 확인되는 변화 | 문서 쪽에서 확인되는 변화 |
| --- | --- | --- |
| 포털에서 신청 성공 | 새 신청 접수 | 이관 처리 중으로 전환 |
| 관리자 최종 확인에서 취소 | 심사 요청을 전송하지 않음 | 변경 요청 없음 |
| 관리자 승인 성공 | 승인 결과와 사유 저장 | 이 승인 메서드에는 문서 상태 갱신이 없음 |
| 관리자 반려 성공 | 반려 결과와 사유 저장 | 해당 신청에 연결된 문서 활성 복구 |

같은 가상 문서를 승인했을 때와 반려했을 때 두 상태가 어떻게 달라지는지 직접 비교할 수 있다. [DocuON 이관 신청·심사 예제](/projects/docuon/#transfer-demo)

## 사유 255의 단위

승인과 반려에는 작은 공통 규칙이 있다. 사유는 필수이며 `TransferApprovalModal.vue`는 `TextEncoder`로 인코딩한 결과가 255바이트 이하인지 확인한다. 상담 메모처럼 한글을 흔히 입력하는 칸에서는 ‘최대 255자’라고 써 두면 사용자가 이해한 제한과 실제 동작이 달라진다.

가령 완성형 한글 ‘가’ 85자는 UTF-8에서 정확히 255바이트라 길이 검사를 통과한다. 여기에 마침표 하나를 보태면 256바이트다. 영문 소문자 `a`는 255개를 적어도 255바이트다. 입력 안내를 붙인다면 검사에 사용한 바이트 수를 보여줘야 사용자가 어느 정도 더 쓸 수 있는지 가늠할 수 있다.

신청자는 문서 두 개를 보냈다고 생각할 수 있고, 운영자는 신청 하나를 승인했다고 기억할 수 있다. 이 예시에서 파일은 두 개, 문서는 하나, 승인도 한 번이다. 화면에 단위를 적고 ‘완료’ 앞에 업무명을 붙이면 두 사람이 같은 내역을 보고 대화할 수 있다.
