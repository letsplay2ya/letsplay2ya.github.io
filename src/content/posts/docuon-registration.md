문서 등록 화면에 첨부 11개를 추가했다. 한 페이지에 10개씩 보이니 2페이지에는 마지막 파일 한 개만 남는다. 그 옆의 삭제 아이콘을 눌렀더니 남은 첨부는 예상대로 10개였다. **빠진 파일은 첫 번째 파일이었다. 누른 파일은 전송 목록에 그대로 있었다.**

DocuON 포털의 Vue 컴포넌트를 분리해 가상 파일로 확인한 결과다. 운영 자료를 볼 필요 없이, 표가 부모에 넘긴 숫자 하나를 추적하면 어떤 일이 일어났는지 설명할 수 있다.

## 파일 두 개를 붙이고 하나를 빼 보면

등록 화면은 파일을 선택할 때 표에 쓸 이름·종류·표시 크기를 한 배열에 넣고, 브라우저가 건넨 `File` 객체를 다른 배열의 같은 위치에 넣는다. 삭제 함수는 전달받은 번호로 양쪽 배열에서 한 건씩 지운다. 파일이 두 개이고 표의 순서를 바꾸지 않았다면 두 번째 행의 인덱스는 1이고, 전체 배열에서도 지워야 할 위치는 1이다. 이 조건으로만 시험하면 양쪽이 모두 맞는다.

파일을 열한 개로 늘리면 표와 부모가 서로 다른 범위에서 인덱스를 센다. 공통 표 `DataTable.vue`는 전체 배열에서 현재 페이지 부분을 먼저 잘라 Vuetify 테이블에 넘긴다. 셀 슬롯의 `index`는 그 조각 안에서 센 행 번호다. 등록 화면에 있는 삭제 아이콘은 이 값을 그대로 전체 배열의 삭제 함수에 전달한다.

| 10개씩 표시할 때 | 1페이지 둘째 행 | 2페이지 첫째 행 |
| --- | ---: | ---: |
| 사용자가 누른 첨부 번호 | 02 | 11 |
| 셀 슬롯의 인덱스 | 1 | 0 |
| 전체 배열에서 지워야 할 인덱스 | 1 | 10 |
| 기존 함수로 빠진 첨부 번호 | 02 | 01 |

삭제 후 두 배열은 여전히 길이가 같고 같은 순서로 정렬돼 있다. `files.length === fileList.length`도 통과한다. 틀어진 관계는 표시 배열과 파일 배열 사이가 아니라 **사용자가 누른 행과 함수가 제거한 항목 사이**에 있다.

## 어떤 파일을 보낼지 확인하는 시험

원본 포털에서 사용한 Vue 3.5.13과 Vuetify 3.7.1 환경에서 공통 표와 모바일 카드, 등록 화면의 첨부 선택·삭제 함수와 셀 슬롯을 분리해 브라우저에서 실행했다. 파일명은 `sample-01.txt`부터 `sample-11.txt`까지 붙였다. 2페이지 첫 행의 삭제 아이콘을 누른 뒤 표시 목록과 실제 파일 배열 양쪽에 **02부터 11**까지 남았다. 남은 파일을 시험용 `FormData`에 담고 `getAll('files')`로 다시 꺼내도 같은 순서였다. 이 시험은 첨부 처리까지 실행했다. 서명 모듈과 등록 서버는 호출하지 않았다.

모바일에는 다른 조건이 있었다. 부모는 카드에 삭제 버튼용 `actions` 슬롯을 제공하지만, `CardListMo.vue`는 전달받은 표시 필드별 슬롯만 렌더링한다. 등록 화면이 넘기는 필드는 종류·파일명·크기다. 분리 실행한 모바일 카드에서 삭제 아이콘은 0개였다. 모바일 검증의 첫 항목은 ‘무엇을 삭제했나’보다 앞에 있다. **사용자가 해당 조작을 시작할 수 있는가?**

위의 공개 예제는 이 결과를 비교할 수 있게 새로 만든 작은 Vue 화면이다. ‘01번과 11번의 이름을 같게 하기’를 선택하면 두 파일은 이름·확장자·표시 크기까지 같아진다. 본문에는 각각 두 자리 표식 `01`과 `11`을 썼다. 두 방식 모두 전송할 파일이 열 개이고 이름 목록에 `점검표.txt`가 하나씩 있어도, 실제로 남은 파일은 본문 표식으로 구별할 수 있다. [첨부 삭제 비교 예제](#attachment-review)

## 인덱스를 고칠까, 파일을 가리키는 값을 넘길까

지금의 무정렬 예시에서는 `(페이지 − 1) × 10 + 행 인덱스`로 전체 위치를 구할 수 있다. 2페이지의 첫 행은 `(2 − 1) × 10 + 0 = 10`이다. 간단하지만 표가 정렬이나 필터링을 맡게 되면 화면 순서와 선택 당시의 순서가 또 달라질 수 있다.

비교 예제의 다른 경로는 각 첨부에 선택 시점의 고유한 ID를 붙인다. ID와 실제 파일을 한 레코드에 보관하고, 삭제 버튼이 해당 행의 ID를 돌려주면 그 레코드만 제외한다. 표시 목록과 전송 목록은 남은 레코드에서 읽는다. 같은 이름의 파일을 두 번 선택해도 각 선택을 구별할 수 있다. 이 규칙을 실제 화면에 적용한다면 PC 셀과 모바일 카드가 같은 ID를 부모에게 전달하도록 양쪽 슬롯을 함께 고쳐야 한다. 여기서 제시한 변경은 포트폴리오에서 비교한 대안이다.

## 서명에 넘기는 값과 등록 요청에 담는 값

이 삭제 문제가 중요한 이유는 이후 단계가 선택 결과를 다시 검산하지 않기 때문이다. 등록 버튼을 누르면 연도와 개월이 모두 0인지, 첨부가 한 개 이상인지, 제목과 키워드에 내용이 있는지를 검사한다. 11개 중 다른 한 개를 지웠더라도 남은 열 개는 첨부 개수 조건을 만족한다.

예를 들어 1년 6개월을 선택하면 서명 입력에는 총 18개월이 들어간다. `buildSignString`은 다른 문서 정보와 함께 **남은 표시 목록의 파일 이름들**을 문자열로 만든다. 다음 단계의 `postDocument`는 문서 정보와 서명 결과를 JSON으로 만들고, 실제 파일 배열을 순회해 각 파일을 같은 이름의 multipart 필드에 추가한다. 두 배열에서 01번이 함께 빠졌다면 양쪽 모두 02~11번을 가리킨다. 두 목록이 일관돼도 사용자가 원했던 01~10번과는 다르다.

## 첫 번째 안내를 닫아야 저장 요청이 시작된다

전자서명 콜백이 실패하면 오류 처리 후 돌아간다. 성공하면 서명 결과를 보관하고 인증 완료 안내를 띄운다. 사용자가 안내를 확인해야 등록 함수가 호출된다. 등록 성공 응답을 받은 뒤에는 또 하나의 안내를 띄우고, 이를 확인하면 응답이 돌려준 정보로 증명서 상세를 연다. 등록 화면 시험에서 ‘성공 안내를 봤다’는 관찰만 남기면 어느 구간을 확인한 것인지 모호해진다.

이 사례의 회귀 시험이라면 세 가지를 함께 적겠다. **어느 페이지의 어느 파일을 눌렀는지, 남은 이름이 서명 입력에 어떻게 들어가는지, 전송할 파일 본문 중 무엇이 남았는지.** 첫 페이지 두 건만으로 지나갔던 문제가 두 번째 페이지 첫 행과 같은 이름 두 건에서 드러난다. [DocuON 프로젝트 기록](/projects/docuon/)
