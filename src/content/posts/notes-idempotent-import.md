파일 적재가 끝났는데 응답을 받지 못했다. 같은 파일을 다시 넣었을 때 두 건이 생기면 곤란하다. 그렇다고 같은 ID라는 이유로 모두 버리면 금액이 수정된 파일도 조용히 무시할 수 있다.

[이전 CSV 실습](/writing/legacy-oracle-ch3/)은 이미 저장된 ID를 DUPLICATE_ID로 거절했다. 추가 삽입은 막았지만 같은 내용의 재시도와 다른 내용의 충돌은 구분하지 않았다. 이번에는 그 차이를 Python 표준 라이브러리와 SQLite로 분리했다. 전체 적재 시스템을 확장한 코드가 아니라 **한 레코드의 쓰기 경계**를 검증하는 별도 실습이다.

## ID와 내용을 따로 비교한다

| 저장된 ID | 정규화한 내용 | 결과 | 기존 데이터 |
| --- | --- | --- | --- |
| 없음 | 유효함 | created | 새로 저장 |
| 있음 | 동일함 | replayed | 유지 |
| 있음 | 다름 | conflict | 유지 |
| 관계없음 | 유효하지 않음 | 검증 예외 | 변경하지 않음 |

replayed는 “이미 이 내용으로 처리했다”는 뜻이다. conflict는 “이 ID로 다른 내용이 존재한다”는 뜻이다. 둘을 같은 성공이나 같은 오류로 묶지 않는다. 충돌을 자동 수정으로 바꾸지 않는 이유는 어떤 파일이 최신인지, 수정 권한이 있는지 이 입력만으로 판단할 수 없기 때문이다.

단, 이 예제의 키는 업무 record_id다. 요청마다 따로 발급하는 멱등 키와 같지 않다. 다른 ID로 같은 내용을 보내면 새 레코드로 저장한다. 사용자 요청 전체를 식별하거나 이전 HTTP 응답을 그대로 재생하는 서비스는 아니다.

## 원본 문자열을 비교할까, 정규화 결과를 비교할까

25.50과 025.5는 같은 금액으로 처리한다. 회사명의 앞뒤 공백도 제거한다. 이 때문에 문자열이 달라도 정규화한 날짜·최소 단위 금액·회사명이 같으면 replayed가 된다.

| 입력 변경 | 판정 | 이유 |
| --- | --- | --- |
| 25.50 → 025.5 | replayed | 둘 다 최소 단위 정수 2550 |
| 회사명 앞뒤 공백 추가 | replayed | 명세에서 공백 제거 |
| 금액 25.50 → 26 | conflict | 금액이 달라짐 |
| 같은 ID의 날짜 변경 | conflict | 비교 대상 내용이 달라짐 |
| 새 ID로 같은 내용 전달 | created | 이 실습은 ID별 일관성만 판단 |

정규화가 넓으면 의미 있는 차이까지 지울 수 있다. 회사명 내부 공백, 대소문자, Unicode 정규화는 이 예제에서 임의로 합치지 않는다. 비교에 포함하는 필드를 바꾸는 일도 정책 변경이다. 나중에 새 필드가 추가됐는데 비교 목록에서 빠지면 다른 내용을 같은 요청으로 오판할 수 있다.

금액은 Decimal로 해석한 뒤 정수로 저장한다. 이 정책은 소수 둘째 자리까지 허용하는 샘플에 맞춘 것이며 통화별 소수 자릿수나 환율을 모델링한 것은 아니다.

## SELECT 다음 INSERT 사이에 다른 요청이 들어오면

메모리의 ID 집합이나 잠금 없는 사전 조회만으로 동시 실행을 해결할 수는 없다. 두 연결이 모두 “없음”을 읽은 뒤 각각 삽입하려 할 수 있다. DB의 유일 제약은 중복 행을 막지만, 서비스가 그 실패를 어떤 결과로 해석할지는 남는다.

이번 실습은 SQLite의 BEGIN IMMEDIATE로 짧은 검사·쓰기 구간을 먼저 확보한다. [SQLite 트랜잭션 문서](https://www.sqlite.org/lang_transaction.html)에서 설명하는 쓰기 트랜잭션 특성을 사용한 선택이다. 첫 번째 쓰기가 끝난 뒤 다음 연결이 최신 저장값을 읽어 replayed 또는 conflict를 결정한다.

```text
내용 검증·정규화
  → BEGIN IMMEDIATE
  → 현재 ID의 저장 내용 조회
  → 없음: INSERT / 같음: replayed / 다름: conflict
  → COMMIT
```

정규화는 잠금 전에 끝내고, 잠금을 가진 동안 외부 API나 파일 다운로드를 하지 않는다. 트랜잭션을 짧게 유지하는 이유다. 함수가 호출자 트랜잭션을 몰래 커밋하지 않도록, 이미 트랜잭션이 있으면 명시적으로 거절한다.

이 선택을 Oracle이나 PostgreSQL의 일반 해법으로 옮기지는 않는다. 잠금 범위와 충돌 처리 방식이 다르며, SQLite의 쓰기 직렬화는 처리량 면에서도 비용이 있다. 다른 DB에서는 유일 제약 충돌 이후 재조회나 격리·잠금 정책을 해당 DB에서 검증해야 한다.

## 먼저 도착한 값과 올바른 값은 다르다

동시 요청의 내용이 서로 다르면 먼저 쓰기 경계를 확보한 값이 남는다. 테스트는 어느 스레드가 이길지 고정하지 않는다. created 한 건과 conflict 한 건, 최종 행 한 건만 확인하며 저장된 금액은 두 후보 중 하나여야 한다.

선착순은 충돌을 발견하는 정책이지 최신 버전이나 업무적 정답을 판정하는 정책이 아니다. 수정이 필요하면 버전 번호·원본 버전 조건·승인 이력 같은 추가 정보가 필요하다. 무조건 upsert로 바꾸면 충돌을 숨긴 채 늦은 파일이 최신 데이터를 덮을 수 있다.

## 실제 두 연결로 확인했다

[실행 코드](/examples/idempotent-import/pipeline.py), [테스트](/examples/idempotent-import/test_pipeline.py), [안내](/examples/idempotent-import/README.md)를 같은 폴더에 두고 실행할 수 있다. DB 서버나 외부 Python 패키지는 필요 없다.

```sh
python -B -m unittest discover -s . -p "test_*.py"
```

8개 테스트는 다음을 확인한다.

- 정규화한 동일 내용의 재시도는 한 행 유지
- 금액·회사·날짜 충돌이 기존 내용을 덮지 않음
- 다른 키는 새 레코드로 처리
- 잘못된 입력은 쓰기 전에 거절
- INSERT 실패 주입 시 롤백하고 트랜잭션 종료
- 호출자 트랜잭션을 허용하지 않는 함수 계약
- 같은 내용으로 두 연결이 경쟁하면 created + replayed
- 다른 내용으로 두 연결이 경쟁하면 created + conflict

동시성 테스트는 별도 연결과 임시 파일 DB를 만들고 barrier로 두 쓰기의 출발을 맞춘다. 상태표만 흉내 내는 테스트가 아니다. 다만 두 동시 쓰기를 확인한 것이 고부하·다중 프로세스·장시간 잠금 상황의 성능 검증은 아니다.

## 잠금 대기는 재시도 정책이 아니다

연결의 timeout은 3초다. 기다려도 쓰기 경계를 얻지 못하면 실패할 수 있다. timeout을 설정했다고 자동으로 안전한 재시도가 생기지는 않는다. 재시도 횟수·간격·요청 식별·최종 실패 기록을 별도로 결정해야 한다.

내용이 conflict인 경우와 잠금 때문에 처리 여부를 확정하지 못한 경우도 다르다. 둘을 같은 “중복” 메시지로 반환하면 사용자가 수정해야 할지 다시 시도해야 할지 알 수 없다. 실제 서비스의 오류 계약은 저장 상태와 연결해서 정해야 한다.

## 파일 전체의 멱등성은 남아 있다

이 함수의 원자성은 한 레코드 단위다. 파일의 앞부분을 저장한 뒤 뒷부분이 실패하면 앞부분은 남는다. 파일 전체 롤백, 배치 ID, 원본 파일 보관, 거절 로그, 재시작 위치를 구현한 것은 아니다.

앞선 CSV 예제와 이번 실습을 단순히 이어 붙여 완성된 적재기로 소개하지 않는 이유다. 두 예제는 각각 파일·트랜잭션 정책과 한 키의 내용 충돌을 보여 준다. 다음 단계는 이 두 경계를 어떤 배치 정책으로 결합할지 정하는 일이다.
