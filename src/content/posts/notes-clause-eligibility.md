약관 화면에서 적용을 체크했다. 요율 화면으로 이동했는데 해당 약관이 할인할증 목록에 없다. 두 화면의 값이 어긋났다고 단정하기 쉽지만, 먼저 물을 것은 **적용한 약관이 모두 할인할증 대상인가**다.

코리안리 약관 화면의 파생 항목 판정은 적용 체크 하나보다 많은 조건을 읽는다. 적용 레벨, 적용 여부, 할인할증 대상 플래그가 함께 쓰인다. 현재 계약에 적용하는 것과 산정용 파생 항목을 만드는 것은 다른 판단이다. 이 구분을 놓치면 화면 간 동기화를 구현하면서 오히려 잘못된 행을 추가할 수 있다.

## 체크박스 세 개로 생각하면 놓치는 것

코드에서 사용하는 주요 값은 다음과 같다. 코드값의 세부 업무 명칭은 추정하지 않고, 확인한 분기 자체로 설명한다.

| 필드 | 이 흐름에서 하는 일 | 판정과의 관계 |
| --- | --- | --- |
| appYn | 약관 적용 여부 | Y인 경우에만 대상이 될 수 있음 |
| clusDcExchgExsoYn | 할인할증 대상 플래그 | Y 또는 누락·빈 값 허용 |
| appLevlDvCd | 적용 레벨 | 04이면 제외 |
| appOptnYn | 화면에서 다루는 선택 값 | 대상 판정 함수에는 사용하지 않음 |

UI 안에서는 적용·선택을 boolean으로 다루는 부분이 있지만, API 형태로 변환할 때 Y/N 문자열로 되돌린다. 화면의 체크 상태, 전송 형식, 파생 목록의 포함 조건을 같은 변수 하나로 줄여 설명할 수 없는 이유다.

## 원본 판정은 짧지만 정책은 짧지 않다

다음은 원본 판정 함수다. 예제에서는 업무 API 전체 타입 대신 이 함수가 읽는 세 필드만 선언했다.

```ts
type ClauseEligibilityInput = {
  appLevlDvCd?: string;
  appYn?: string;
  clusDcExchgExsoYn?: string;
};
const toUpperText = (value: unknown) => String(value ?? '').trim().toUpperCase();
const isDerivedClauseDiscountTarget = (term: ClauseEligibilityInput) => {
  const discountTargetYn = toUpperText(term.clusDcExchgExsoYn);
  return (
    toUpperText(term.appLevlDvCd) !== '04' &&
    toUpperText(term.appYn) === 'Y' &&
    (discountTargetYn === '' || discountTargetYn === 'Y')
  );
};
```

| 적용 레벨 | 적용 여부 | 대상 플래그 | 결과 |
| --- | --- | --- | --- |
| 03 | Y | Y | 포함 |
| 03 | Y | N | 제외 |
| 03 | Y | 누락 | 포함 |
| 03 | N | Y | 제외 |
| 04 | Y | Y | 제외 |
| 03 | Y | 예상 밖 문자열 | 제외 |

함수는 공백과 대소문자를 정규화한다. 예를 들어 ` y `는 Y로 읽는다. 반면 문자열 1이나 true를 Y로 변환하지는 않는다. 입력을 넓게 받아들이는 도우미라고 생각하고 다른 형식을 넘기면 판정이 달라질 수 있다.

### 누락과 N을 같은 false로 바꾸면 생기는 차이

원본 주석에는 이전 Reference 스냅샷에 대상 플래그가 없을 수 있다고 적혀 있다. 그래서 누락을 곧바로 제외하지 않고 다른 적용 조건으로 판단한다. 예전 스냅샷의 누락과 최신 응답의 명시적인 N을 같은 false로 바꾸면, 과거 작업을 복원할 때 포함됐어야 할 파생 행이 사라질 수 있다.

이는 “모든 누락값은 허용하자”는 일반 규칙이 아니다. appYn은 누락되면 Y가 아니므로 제외된다. appLevlDvCd가 누락되면 04가 아니므로 이 조건은 통과한다. 같은 객체 안에서도 필드별 누락 정책이 다르다. 더 엄격한 입력 검증이 필요해지면 이 판정 전에 별도의 유효성 검사를 두어야 한다.

예제 상단에서 적용을 유지한 채 대상 플래그만 누락에서 N으로 바꾸면 결과가 달라진다. 레벨을 04로 바꾸면 플래그가 Y여도 제외된다. 이 예제는 대상 판정만 실행하며 보험료나 실제 계약을 저장하지 않는다.

## 행이 아니라 변경 전후의 대상 집합을 비교하기

원본의 getEligibleNonGlTermsByKey는 대상 조건을 통과한 약관을 증권 코드와 약관 코드의 조합으로 묶는다. 두 코드 중 하나라도 비어 있으면 대상 Map에 넣지 않는다. 위 판정 함수가 true를 반환했다고 해서 파생 행을 무조건 생성하는 것은 아니다.

변경 처리는 대략 다음 흐름이다.

```text
이전 약관 목록 → 유효한 키 + 대상 조건 → 이전 대상 Map
다음 약관 목록 → 유효한 키 + 대상 조건 → 다음 대상 Map

이전에는 없고 다음에는 있음 → 파생 행 추가 후보
이전에는 있고 다음에는 없음 → 파생 행 삭제 후보
계속 대상이며 선택 값이 바뀜 → 선택 값 갱신 후보
```

예시로 세 항목을 보자. 이름과 코드는 설명용 가상 값이다.

| 변경 전 대상 | 사용자의 변경 | 변경 후 대상 | 파생 목록에서 할 일 |
| --- | --- | --- | --- |
| P-A / C-1 포함 | 적용 해제 | 제외 | 해당 파생 행 제거 |
| P-A / C-2 제외 | 적용 Y, 대상 Y로 변경 | 포함 | 같은 키가 없으면 추가 |
| P-B / C-1 포함 | 선택 값만 변경 | 포함 | 기존 파생 행의 선택 값 갱신 |

약관 코드 C-1이 같아도 증권 P-A와 P-B는 다른 키다. 화면의 행 번호로 비교하면 정렬이나 참고 약관 복사 후 다른 항목을 수정할 수 있다. 구현은 배열 위치 대신 JSON.stringify([plcyCd, clusCd]) 형태의 키를 사용한다.

여기에도 경계가 있다. Map에는 같은 키가 여러 번 들어오면 뒤의 항목이 남는다. 서로 다른 적용 레벨의 항목을 같은 증권·약관 코드로 동시에 구별해야 하는 요구라면 현재 키가 충분한지 확인해야 한다. 현재 코드를 “모든 약관을 유일하게 식별한다”고 일반화하지 않는다.

## 지울 때는 파생 행만 지운다

applyTermClauseDeltaToCoverages는 제거 대상 키가 일치하더라도 모든 행을 삭제하지 않는다. 기존 할인할증 행의 clusAppLevlDvCd가 03인 경우에 제거 조건을 적용한다. 대상 판정에서 읽은 **appLevlDvCd**와 기존 행의 파생 범위를 구분하는 **clusAppLevlDvCd**는 이름도 역할도 다르다.

이 조건이 빠지면 같은 코드의 다른 레벨 행까지 함께 없앨 수 있다. 반대로 제거 대상을 찾을 수 없는 빈 키의 행은 이 삭제 조건으로 제거되지 않는다. 삭제가 보수적으로 보인다는 이유로 필터를 단순화하기 전에 어떤 행을 이 흐름이 소유하는지 확인해야 한다.

일괄 교체 경로는 이전 대상 키를 제거 후보로, 다음 대상을 추가 후보로 삼아 파생 행을 다시 구성한다. 일반 변경 경로와 같은 처리라고 생각하면 기존 계수 보존 여부를 잘못 예상하게 된다.

## 모든 속성 변경이 같은 갱신은 아니다

일반 변경에서 추가·갱신 후보로 잡는 것은 새로 대상이 된 항목과 appOptnYn이 바뀐 항목이다. 같은 키가 계속 대상이고 계수 값만 바뀌었다면 이 조건만으로 신규 후보가 되지 않는다. 기존 행에 후보가 있더라도 이 helper가 직접 갱신하는 속성은 선택 값이다.

따라서 “약관의 모든 필드가 요율 목록과 항상 실시간으로 같아진다”는 설명은 맞지 않는다. 같은 키의 계수 변경이 어느 경로로 반영돼야 하는지, 일괄 교체를 사용해야 하는지, 기존 편집 계수를 보존해야 하는지는 별도 요구로 확인할 부분이다.

계수 정규화도 검증과 구분해야 한다. normalizeClauseFactor는 빈 값이나 숫자 0을 문자열 1로 바꾸지만, 임의의 잘못된 문자열을 모두 거절하는 함수는 아니다. 1이 기본 계수라는 처리와 입력값 전체의 유효성 보장은 같은 말이 아니다.

## 요율 화면의 편집값을 먼저 읽는 이유

DNO 분기는 현재 UW와 요율 store의 ownerUwNo를 비교한다. 소유 계약이 같고 해당 탭의 약관 편집값이 있으면 그 값을 상세 데이터에 가져온 뒤 변경분을 적용한다. 화면에서 이미 수정한 계수를 오래된 상세 데이터로 덮지 않기 위한 흐름으로 읽을 수 있다.

변경 결과는 상세 store와 요율 탭 상태 양쪽에 반영하며, 저장용 행에서는 UI용 id를 제거한다. 같은 약관 변경이라도 데이터가 한 배열에만 있는 것이 아니므로, 필터 결과가 맞는 것과 편집 화면·전송 데이터가 함께 맞는 것은 별도의 확인 대상이다.

이 글이 설명한 대상 Map과 delta 처리는 일반 책임배상 분기를 제외한 흐름이다. 원본은 상품군에 따라 별도 처리로 보내거나 여기서 처리를 종료한다. 한 helper의 정책을 모든 보험 종목에 그대로 적용하는 규칙으로 소개하지 않는다.

## 무엇을 검증했나

판정 함수는 적용 여부·레벨·대상 플래그의 36개 조합과 공백·대소문자·누락 경계를 실행했다. 글에 실린 코드와 화면에서 사용하는 함수에 같은 기대값을 적용한다. 실행 방법은 저장소에서 `npm run test:workflow`다.

파생 목록의 변경 처리는 원본 소스를 분석한 설명이다. 판정 함수 테스트가 store 간 갱신이나 서버 저장까지 검증하는 것은 아니다. 후속 회귀 검증은 적용 해제 시 해당 파생 행만 제거되는지, 동일 약관 코드의 다른 증권이 유지되는지, 같은 키의 계수 수정이 정해진 정책대로 반영되는지를 포함해야 한다.
