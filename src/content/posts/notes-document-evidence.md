문서에서 추출한 계약 정보를 검토할 때는 값이 나온 위치와 주변 문맥을 함께 확인할 수 있어야 합니다. [코리안리 특종보험 프로젝트](/projects/koreanre-ai-assistant/)에서는 OCR 항목에서 원문 PDF의 근거로 이동하는 화면을 구성했습니다.

## 추출값에 근거 위치 연결하기

OCR 항목에는 추출값과 함께 문서 ID, 페이지 번호, 좌표 목록이 연결되어 있습니다. 사용자가 항목의 근거를 선택하면 먼저 해당 문서를 활성화하고, 페이지로 이동한 뒤 원문 영역에 하이라이트를 표시합니다.

한 항목의 근거는 하나의 문서나 위치에 한정되지 않을 수 있습니다. 활성 항목, 활성 문서, 근거 목록에서의 현재 위치를 구분하고 이전·다음 근거를 탐색할 때 문서도 함께 전환하도록 구성했습니다.

## 이미지 좌표를 페이지 비율로 바꾸기

추출 좌표는 원본 이미지의 크기를 기준으로 전달됩니다. 표시 영역의 크기와 연결하기 위해 왼쪽·위쪽 위치, 너비와 높이를 원본 이미지 너비·높이에 대한 백분율로 변환합니다. 페이지 번호도 PDF 뷰어가 사용하는 0부터 시작하는 인덱스로 바꿉니다.

```ts
// 좌표 변환의 핵심을 설명하는 축약 예시입니다.
function toPercent(
  rect: { x: number; y: number; width: number; height: number },
  page: { width: number; height: number },
) {
  return {
    left: (rect.x / page.width) * 100,
    top: (rect.y / page.height) * 100,
    width: (rect.width / page.width) * 100,
    height: (rect.height / page.height) * 100,
  };
}
```

실제 구현은 좌표 정보의 이미지 크기를 읽고, 누락된 크기의 기본값과 0 이하 크기에 대한 대체값을 적용합니다. 활성 문서와 같은 문서 ID의 근거만 하이라이트 대상으로 남깁니다. PDF 뷰어의 하이라이트 플러그인이 제공하는 좌표 스타일을 사용해 해당 페이지 위에 표시합니다.

## 페이지 이동과 조회 상태 다루기

근거를 바꿨을 때 문서 로딩과 페이지 렌더 시점이 맞아야 합니다. 페이지 이동을 프레임에 맞춰 예약하고 재시도하며, 새로운 이동이나 화면 해제 시에는 이전 예약을 정리합니다.

OCR 기본정보와 파일 목록은 병렬로 가져옵니다. 계약을 빠르게 전환하면 이전 조회의 응답이 늦게 도착할 수 있으므로 요청 버전과 현재 UW 번호를 함께 확인합니다. 현재 조회에 해당하는 응답만 화면 상태에 반영합니다.

이 흐름은 항목 선택 → 문서 선택 → 페이지 이동 → 근거 표시로 이어집니다. 사용자는 추출된 값만 읽는 데서 멈추지 않고 해당 값의 원문 문맥을 확인할 수 있습니다.

## 원본 좌표는 너비·높이가 아니라 두 모서리다

위 toPercent 예시는 사각형을 x·y·width·height로 받는다. 실제 API 좌표는 cdntVlu1·2를 시작점, cdntVlu3·4를 끝점으로 읽는다. 원본은 끝점에서 시작점을 빼 너비와 높이를 구한다. 세 번째 값을 곧바로 width로 쓰면 강조 영역이 커진다.

가상 문서 A의 2페이지가 1000×1400이고 좌표가 (100, 280)에서 (400, 420)이라고 하자.

| 값 | 원본 픽셀 | 페이지 비율 | 500×700 표시에서의 위치 |
| --- | --- | --- | --- |
| 왼쪽 | 100 | 10% | 50px |
| 위쪽 | 280 | 20% | 140px |
| 너비 | 400 - 100 = 300 | 30% | 150px |
| 높이 | 420 - 280 = 140 | 10% | 70px |

계산 기준은 OCR 이미지의 너비·높이다. 저장소의 PDF 표시용 페이지 크기와 이름이 비슷해도 같은 좌표계라고 가정해서는 안 된다. 원본은 하이라이트 플러그인의 getCssProperties에 영역과 회전값을 전달한다. 위 표의 단순 확대 계산이 회전·잘림·OCR 이미지 여백 차이까지 직접 해결하는 것은 아니다.

## 문서와 페이지와 근거 순번을 함께 보기

2페이지라는 번호는 문서 A와 B에 각각 존재한다. 따라서 페이지 인덱스만 맞아도 다른 문서에 표시하면 틀린 근거다. 원본은 pos.ocrId와 활성 문서 ID가 같은 근거만 남기고, 그 뒤 현재 렌더 페이지의 pageIndex로 다시 거른다.

한 항목의 근거 목록이 A의 2페이지, B의 1페이지, A의 3페이지 순이라면 A 문서에서 남는 근거 순번은 0과 2다. 원본은 문서 필터 전에 pointIndex를 부여하므로 이 순번을 유지한다. 필터한 배열을 다시 0·1로 번호 매겨 활성 근거 순번과 비교하면, 세 번째 근거를 선택했는데 강조가 빠지는 식의 오류를 만들 수 있다.

선택한 항목, 그 항목의 근거 커서, 활성 문서는 서로 연결되지만 별도 상태다. 이전·다음 버튼은 커서뿐 아니라 해당 근거의 문서 ID도 바꾼다. 근거가 없는 항목에서는 바로 종료하여 잘못된 문서 이동을 만들지 않는다.

## 기본값 처리로 좌표가 유효해지는 것은 아니다

원본은 이미지 크기가 없을 때 1653×2339를 사용하고, 숫자로 해석한 크기가 양수가 아니면 분모를 1로 바꾼다. 0으로 나누는 일을 피하지만, 실제 크기를 모르는 문서의 위치가 정확해진다는 뜻은 아니다.

입력 타입에 따른 차이도 있다. 숫자 0은 기본값 선택의 ||에서 대체되지만 문자열 '0'은 그 단계를 통과한 뒤 0으로 변환되어 분모 1을 사용한다. 끝점이 시작점보다 작으면 음수 너비가 나오고, 좌표에 잘못된 문자열이 있으면 NaN이 나올 수 있다. 원본 변환은 이를 모두 거절하거나 페이지 안으로 잘라 주는 검증기가 아니다.

새 입력을 받는 경계에서는 이미지 크기의 유한성·양수 여부, 모서리 순서, 페이지 범위, 좌표의 페이지 밖 이탈을 별도로 검증할 수 있다. 범위를 벗어난 값을 조용히 잘라 낼지 오류로 보여 줄지도 업무 정책이다. 현재 변환이 이미 그 정책을 구현했다고 설명하지 않는다.

## 페이지 이동의 재시도와 준비 완료는 다르다

원본은 이전 예약을 지운 뒤 requestAnimationFrame에서 이동을 요청하고, 160ms 후 한 번 더 이동을 시도한다. 문서 변경이나 화면 해제에서는 예약된 프레임과 타이머를 정리한다. 고정 지연을 두 번 시도한다는 것이 모든 문서의 로딩 완료를 보장하는 프로토콜은 아니다.

큰 문서나 느린 로딩에서 요구가 더 엄격해지면 문서 준비·페이지 수·렌더 완료와 목표 페이지를 연결하는 확인 절차가 필요하다. 현재 구현의 재시도와 향후 필요한 준비 확인을 같은 기능으로 쓰지 않는 것이 중요하다.

## 같은 계약으로 돌아와도 요청 버전은 다르다

uwOcrStore는 기본정보와 파일 목록을 Promise.all로 조회한 뒤 현재 요청 버전과 UW 번호를 함께 비교한다. A → B → A로 빠르게 이동하면 처음 A와 마지막 A의 UW 번호는 같지만 버전은 다르다. 계약 번호만 확인하는 것보다 오래된 조회를 구분할 수 있다. clearOcrBasicInfo에서도 버전을 증가시켜 이미 끝난 화면의 요청을 무효화한다.

병렬 조회가 두 응답의 업무적 완전성까지 보장하지는 않는다. API가 error 필드를 포함해 반환하는 경우에는 각각 로그를 남기고 사용 가능한 data 또는 빈 목록을 반영하는 경로가 있다. Promise 자체가 거절되는 경우에는 현재 요청일 때 두 목록을 비운다. 하나의 오류 정책이라고 뭉뚱그리지 말아야 한다.

## 변환 예제를 실행해 보기

[좌표 변환 예제](/examples/document-coordinates/example.mjs), [테스트](/examples/document-coordinates/test.mjs), [안내](/examples/document-coordinates/README.md)를 같은 폴더에 두고 node test.mjs로 실행할 수 있다. 변환 함수는 원본에서 타입을 제거한 것이고, 문서 필터는 명시적인 PDF 타입만 받도록 축소했다.

정상 비율과 페이지 인덱스뿐 아니라 음수 너비·잘못된 문자열·숫자 0과 문자열 0의 차이도 확인한다. 이 부정 입력 테스트는 그런 결과가 올바르다는 주장이 아니라 현재 함수가 보장하지 않는 경계를 보여 준다. 실제 PDF 렌더링, 회전된 문서와 고객 원문을 사용한 검증은 이 예제의 대상이 아니다.

## 확인할 동작

- 한 문서의 다른 페이지와 다른 문서에 있는 근거를 선택했을 때 뷰어가 함께 이동하는지 확인합니다.
- 좌표 비율과 실제 표시 위치가 맞는지 확인합니다.
- 여러 근거가 연결된 항목을 앞뒤로 이동할 때 현재 근거의 강조 상태가 맞는지 확인합니다.
- 근거 위치가 없는 항목에서 잘못된 페이지로 이동하지 않는지 확인합니다.
- 조회 중 다른 계약으로 이동한 후 이전 계약 응답이 현재 화면을 덮어쓰지 않는지 확인합니다.

위 항목은 검증 시나리오이며, 이 글을 작성하며 실제 고객 문서로 통합 테스트를 실행한 결과는 아닙니다.

## 구현 범위

담당한 범위는 **OCR·AI 결과를 검토하는 프론트엔드와 API 연동**입니다. 모델 학습이나 인식 정확도 개선을 이 구현의 성과로 포함하지 않습니다. 검토 시간 단축 수치도 측정한 결과가 없어 기재하지 않았습니다.

AI 결과를 업무에 연결하는 데에는 사용자가 근거를 확인할 수 있는 경로가 필요합니다. 이 화면에서는 추출값·문서·좌표의 관계를 사용자가 직접 탐색할 수 있는 동작으로 만들었습니다.
