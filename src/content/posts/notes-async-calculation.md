계산 API가 성공했더라도 그 결과를 현재 화면에 적용할 수 있는지는 다시 판단해야 합니다. 요청 이후 사용자가 계약을 바꾸거나 입력 조건을 수정했을 수 있기 때문입니다. [코리안리 특종보험 프로젝트](/projects/koreanre-ai-assistant/)의 요율산정 화면에서는 응답 적용 시점에 업무 상태를 대조하도록 구성했습니다.

## 요청할 때와 응답할 때의 조건

현재 계약의 조건 A로 계산을 시작한 후 사용자가 조건 B로 수정했다고 가정합니다. 뒤늦게 도착한 A의 결과를 현재 값에 넣으면 화면의 입력과 계산 결과가 서로 다른 조건을 가리킵니다.

이를 판단하려면 요청을 보냈다는 사실뿐 아니라 어떤 계약의 어떤 대상을 어떤 입력으로 계산했는지 기록해야 합니다. 요청 컨텍스트에 UW 번호, 계산 대상 키, 입력값 서명과 화면 수명을 나타내는 값을 담았습니다.

## 현재 상태를 다시 읽어 비교하기

공통 훅은 응답 적용 시 다음 조건을 확인합니다.

1. 요청을 시작한 화면의 수명이 유지되어 있는가.
2. 현재 계약 번호가 요청 당시와 같은가.
3. 계산 대상 키가 같은가.
4. 계산에 사용한 입력값 서명이 같은가.

실제 계산 화면은 응답을 적용하기 전에 최신 store에서 계약과 대상을 읽고 현재 입력 서명을 다시 만듭니다. 그 값이 요청 컨텍스트와 일치할 때만 결과를 반영합니다. 화면이 해제될 때는 수명 값을 변경해 기존 요청을 무효화합니다.

```ts
// 실제 훅의 판단 조건을 설명하기 위해 축약한 예시입니다.
type Context = {
  epoch: number;
  contract: string;
  target: string;
  signature: string;
};

function canApply(request: Context, current: Context | null) {
  return current !== null
    && request.epoch === current.epoch
    && request.contract === current.contract
    && request.target === current.target
    && request.signature === current.signature;
}
```

여기서 화면 수명 값은 요청마다 증가하는 요청 순번과 다릅니다. 같은 화면에서 동일 입력으로 여러 번 요청한 경우의 응답 순서까지 이 조건으로 판별하지는 않습니다.

## 입력값 서명에 무엇을 넣을 것인가

서명은 계산에 사용한 입력을 구분해야 합니다. 계산 결과처럼 요청 조건이 아닌 값까지 넣으면 결과를 저장한 일이 다음 판단의 입력 변경으로 취급될 수 있습니다. 숫자의 표기 차이도 실제 입력 변경과 구분할 필요가 있습니다.

의료배상 LOL·DED 관련 기존 테스트는 `1,000`과 `1000` 같은 표기를 정규화하고, 기본보험료 계산 결과가 갱신돼도 해당 요청 입력의 서명이 유지되는지 확인합니다. 반대로 한도나 자기부담금 등 실제 요청값을 바꾸면 서명도 달라져야 합니다.

## 같은 조건으로 돌아오면 이전 요청도 통과할 수 있다

현재 컨텍스트를 비교하는 정책은 요청 이력을 모두 기억하지 않는다. 계약과 대상이 같고 입력을 A → B → A로 바꿨다고 하자. 처음 A로 보낸 요청이 마지막에 도착하면 현재 입력 서명도 다시 A이므로 통과할 수 있다. 화면 수명 값도 그대로라면 네 조건이 모두 같기 때문이다.

| 상황 | 현재 조건 대조 | 추가로 필요한 정책 |
| --- | --- | --- |
| 입력 A 요청 후 B로 변경 | 이전 결과 제외 | 현재 구현의 대상 |
| A 요청 후 B를 거쳐 다시 A | 처음 A 결과도 통과 가능 | 입력 변경 세대 또는 요청 순번 |
| 같은 A로 요청 1·2 전송 | 둘 다 통과 가능 | 가장 최근 요청만 적용할지 결정 |
| 화면 해제 후 같은 계약 재진입 | 이전 수명의 요청 제외 | 수명 무효화의 대상 |

같은 입력의 계산이 항상 같은 결과라는 전제가 있다면 첫 A 결과를 받아도 업무적으로 허용할 수 있다. 반면 서버의 기준 데이터나 계산 버전이 바뀔 수 있다면 입력 일치만으로 최신성을 보장할 수 없다. 여기서 필요한 것은 무조건 더 많은 guard가 아니라, 결과를 재사용할 수 있는 조건의 명세다.

## 입력 서명과 effect 의존성은 같은 장치가 아니다

의료배상 서명은 계산 종류, 요율 구분, 통화와 LOL/DED 요청값을 고정된 배열로 직렬화한다. 기본보험료 결과를 제외하는 것은 다른 계산 결과가 갱신됐다는 이유로 아직 유효한 LOL 응답이 버려지지 않게 하는 처리다.

이 사실만으로 자동계산 effect의 반복 실행도 해결됐다고 말할 수는 없다. effect가 넓은 객체 전체를 구독하고 결과 저장이 그 객체를 바꾸면, 응답 판정용 서명이 그대로여도 effect는 다시 실행될 수 있다. 요청을 시작하는 의존성, 이미 진행 중인 같은 입력의 요청을 중복 실행할지, 응답을 받아들일 조건은 별도로 확인해야 한다.

원본 DNO 저장 코드에도 편집마다 상세 ojtList에 쓰면 해당 값을 의존하는 자동계산이 다시 실행될 수 있어 저장 직전 병합한다는 주석이 있다. 이 역시 서명 하나로 모든 반응성 문제를 해결하는 구조가 아니라, 쓰기 위치와 구독 범위를 함께 조정하는 사례다.

### 숫자 정규화는 검증이 아니다

원본 toCompactNumberString은 쉼표·공백·% 문자를 제거한 뒤 Number로 변환하고, 유한한 값이면 문자열로 되돌린다. 그래서 1,000과 1000은 같지만 1%를 0.01로 해석하지는 않는다. 숫자가 아닌 문자열은 그대로 남으며, 공백만 있는 문자열은 제거 뒤 0으로 변환될 수 있다.

이 helper를 금액의 범용 정규화나 입력 검증으로 소개하면 안 된다. 허용 형식, 단위, 큰 정수의 정밀도는 별도로 정해야 한다. 서명에는 실제 요청이 해석하는 값과 같은 의미의 정규화가 필요하다.

## 재현 코드로 확인한 경계

[실행 예제](/examples/calculation-context/example.mjs)와 [검증 코드](/examples/calculation-context/test.mjs)는 계약·대상·수명·입력 불일치의 거절, 동일 조건 요청의 구분 불가, 표기 정규화와 결과 필드 제외를 확인한다. Node.js에서 두 파일을 같은 폴더에 두고 node test.mjs로 실행한다.

예제의 입력 튜플은 설명을 위해 축소했다. 의료배상 전체 API의 필드를 복제한 코드는 아니며, 테스트가 원본 화면의 effect 실행 횟수나 서버 계산 결과까지 검증하지 않는다. 요청 취소·순번 비교는 [별도 응답 순서 글](/writing/notes-response-ordering/)과 [Vue 검색 실습](/writing/notes-vue-search-cleanup/)에서 이어서 다룬다.

## 확인할 동작

- 계산 요청 후 다른 계약으로 전환했을 때 기존 결과가 적용되지 않는지 확인합니다.
- 같은 계약 안에서 계산 대상을 바꾼 경우를 확인합니다.
- 요청 이후 입력값을 변경했을 때 이전 조건의 결과가 반영되지 않는지 확인합니다.
- 화면이 해제된 뒤 도착한 응답을 확인합니다.
- 숫자 표기만 달라진 경우와 실제 요청값이 달라진 경우를 구분해 확인합니다.

기존 테스트 소스에서 입력 서명 검증 사례를 확인했습니다. 위 시나리오 전체를 운영 환경에서 실행했다거나 전체 통합 테스트가 통과했다는 의미는 아닙니다.

## 구현 범위

이 구현은 **응답을 상태에 반영할지 결정하는 기능**입니다. 네트워크 요청을 취소하거나, 동일 입력의 중복 요청 중 가장 나중에 보낸 응답만 적용하도록 순서를 보장하는 기능은 포함하지 않습니다.

비동기 작업의 성공과 현재 화면에 적용 가능한 상태는 별개입니다. 요청 시점의 업무 컨텍스트를 기록하고 응답 시점의 값과 대조하는 기준을 공통화하면, 여러 계산 화면에서도 같은 조건으로 결과를 반영할 수 있습니다.
