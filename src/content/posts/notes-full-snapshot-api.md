상세 화면에서 항목 하나를 지운 뒤 저장했는데 다시 조회하면 되살아난다. 반대로 아직 조회하지 않은 목록을 빈 배열로 보내 기존 항목이 사라질 수도 있다. 두 문제는 모두 “저장 요청이 일부 변경인가, 전체 최신 상태인가”를 합의하지 않았을 때 생길 수 있다.

이 글은 코리안리 Java 백엔드의 통합 저장 소스와 설계 문서를 읽으며 정리한 분석이다. 백엔드를 직접 구현했다는 경력 주장이나 운영 장애 사례는 아니다. 아래 JSON과 식별자는 설명용이다.

## 빈 값의 의미부터 계약으로 정하기

```json
{ "items": [] }
```

이 요청은 부분 수정 API에서 “목록을 비운다”는 의미일 수도 있고, 전체 상태 저장에서는 “현재 목록에 남은 항목이 없다”는 의미일 수 있다. 이름만 보고 결정할 수 없다.

| 요청 상태 | 먼저 정해야 할 의미 |
| --- | --- |
| items 속성 누락 | 유지, 기본값, 또는 잘못된 요청인가 |
| items가 null | 초기화, 미입력, 또는 오류인가 |
| items가 빈 배열 | 명시적 전체 삭제인가 |
| 항목 A가 목록에서 빠짐 | A를 삭제하는가, 그대로 두는가 |

이 표는 특정 프로젝트의 모든 필드에 적용되는 명세가 아니다. API를 정의할 때 질문해야 할 목록이다. UI에서 undefined를 직렬화하면 속성이 빠질 수 있다는 점도 고려한다.

## 전체 상태 저장은 조회 범위와 함께 설계하기

전체 상태로 덮어쓰려면 클라이언트가 전체 상태를 알고 있어야 한다. 조회하지 않은 탭의 기본값을 빈 목록으로 만들어 저장하면, 미조회와 삭제를 혼동할 수 있다.

조회 완료 여부와 사용자가 실제로 비운 상태를 구분하거나, 서버가 요구하는 전체 모델을 먼저 확보하는 방법이 있다. 일부만 수정하는 화면이라면 API도 부분 수정 계약을 제공하는 편이 맞을 수 있다.

## 소스에서 확인한 저장 순서

통합 저장 서비스는 요청의 계약 식별자를 검사하고 최신 계약을 잠근 뒤, 기본정보·상품별 담보·약관을 저장 명령으로 변환한다. 이후 기존 최신본을 아카이빙하고 새 최신본을 삽입한 뒤 재조회한다. 이 흐름은 트랜잭션 서비스 메서드 안에 있다.

현재 설계 문서의 기본 아카이브 모드는 Full Snapshot이고, 상품별 legacy 경로를 선택할 설정도 있다. 실제 운영 설정과 데이터로 동작을 검증한 것은 아니다.

## 트랜잭션과 잠금이 해결하지 않는 문제

트랜잭션은 여러 DB 작업의 성공·실패 경계를 묶는다. Spring의 기본 선언적 트랜잭션에서는 일반적으로 RuntimeException과 Error가 롤백 대상이며, checked 예외 정책은 설정에 따라 다르다. 메서드에 어노테이션이 있다는 것만으로 어떤 예외든 원하는 대로 롤백된다고 단정하지 않는다.

행 잠금은 같은 데이터를 바꾸는 트랜잭션을 조정한다. 그러나 오래된 화면을 가진 사용자가 앞선 저장의 잠금 해제 후 저장하면, 그 요청은 여전히 오래된 내용일 수 있다. 이를 탐지하려면 버전 비교 같은 별도 정책이 필요하다. 해당 프로젝트에 낙관적 버전 검사가 구현되어 있다는 의미는 아니다.

## API 테스트에서 나눠 볼 경우

삭제할 항목을 제외한 저장, 빈 목록 저장, 필수 영역 누락, 잘못된 하위 계약 식별자, 아카이빙 이후 삽입 실패를 각각 확인해야 한다. 단순히 응답이 200인지보다 재조회 결과와 기존 이력의 상태까지 보는 것이 중요하다. 이 목록은 검증 제안이며 이번 글 작성 중 운영 DB에 실행하지 않았다.

분석 근거: 백엔드의 `IntegratedSaveService`, `UwSaveLockService`, `integrated-save-full-snapshot.md`.

참고: [PostgreSQL 명시적 잠금](https://www.postgresql.org/docs/current/explicit-locking.html), [Spring 트랜잭션 롤백 정책](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html).
