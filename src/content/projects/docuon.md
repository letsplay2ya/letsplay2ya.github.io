## 원본 발급과 증명서 발급에서 달라지는 요청

점검이 끝난 뒤 현장 사진을 다시 보내 달라는 요청과, 그날 점검 기록을 등록했다는 증명을 달라는 요청이 들어옵니다. 담당자는 같은 문서 상세 화면을 엽니다. 사진만 확인하려면 첨부 목록에서 사진을 골라 이미지 뷰어를 열고, 원본 제출이나 등록 사실 증명이 필요하면 각각의 발급 절차를 밟습니다.

### 보관 패키지에서 원본을 꺼내는 과정

포털에서 점검표 PDF와 사진을 등록하면 문서 정보, 전자서명 결과, 파일 두 개가 한 요청에 담깁니다. Java 서비스는 첨부를 임시 저장하고 보존기간을 만료 예정일로 환산해 보관을 요청합니다. 등록이 성공하면 보관 시스템이 돌려준 패키지 ID로 나중에 원본을 찾을 수 있습니다. 이때 다운로드 목록에 담기는 것은 최초 등록 증명서입니다.

원본을 제출할 때 Java 서비스는 **문서 ID와 보관 패키지 ID**를 함께 보내고, 보관 시스템이 실제로 반환한 파일 목록으로 다운로드를 구성합니다. 파일 한 개가 오면 그 파일을 그대로 내보내고, 점검표와 사진이 모두 오면 ZIP 한 개를 만듭니다. 증명서 파일이 함께 반환되면 원본 ZIP과 따로 받을 수 있게 목록에 추가합니다. 등록된 문서 수만으로는 다운로드 결과를 정할 수 없는 이유입니다.

### 등록 사실을 증명하는 이력 한 건

증명서가 필요하면 담당자는 문서 상세의 **증적 이력**에서 등록 건을 고릅니다. 증적은 문서에 어떤 처리가 있었는지 남긴 기록입니다. 포털은 처리 유형별 정책을 조회해 신청서에 필요한 칸을 보여줍니다. 예를 들어 운영자가 증명 효력의 만기일을 입력받도록 정한 경우에만 날짜 칸이 나타납니다.

발급을 확정하면 Java 서비스가 활성 정책을 다시 찾아 **선택한 증적의 일련번호**를 보관 시스템에 전달합니다. 요청과 맞는 정책이 없으면 발급은 여기서 멈춥니다. 발급이 끝난 뒤에는 해당 증명서의 ID로 발급 내역을 다시 조회합니다. 같은 점검표에 대해 원본을 받거나, 등록 사실을 증명하거나, 이미 발급한 증명서를 확인할 때 각각 어떤 기록을 찾아야 하는지가 화면과 API에 드러납니다.

운영자 콘솔에서 정책 한 건의 기본 정보와 관련 식별자 목록은 한 트랜잭션으로 저장합니다. 기존 활성 정책을 새 정책으로 교체하는 과정에는 요청이 두 번 필요합니다. 먼저 기존 정책의 비활성화가 성공한 것을 확인한 뒤 새 정책을 저장합니다. 첫 저장과 두 번째 저장 사이를 포함해 어떤 정책이 활성 상태인지는 발급 시점의 서버 조회가 결정합니다.

## 다른 보관소로 옮길 때 승인이 보장하는 범위

담당자가 점검 기록을 다른 보관소로 보내기 위해 목적 보관소와 사유를 제출합니다. 서비스는 신청 한 건을 만들고 점검표와 사진을 각각 연결한 다음 문서를 ‘이관 처리 중’으로 바꿉니다. 한 트랜잭션으로 기록하지만 데이터의 단위는 다릅니다. 관리자 상세에 같은 제목이 두 줄 나타나도 심사할 신청은 하나입니다. [첨부별 이력과 문서별 합계 비교](#transfer-rows)

| 운영자의 판단 | 서버가 기록하는 결과 | 담당자가 확인할 수 있는 사실 |
| --- | --- | --- |
| 승인 | 신청에 심사 결과·처리 사유·심사 시각을 기록 | 보관소 이관이 허가됨. 인계 완료 시각은 별도 기록에서 조회 |
| 반려 | 신청에 심사 결과와 사유를 기록하고 연결된 문서를 이용 가능 상태로 복구 | 반려 사유를 확인하고 원래 문서를 다시 사용 가능 |

운영자가 여러 문서를 일괄 이관하는 경로에서는 처음부터 승인된 신청을 만들면서 각 문서에는 ‘이관 처리 중’을 기록합니다. 원본을 옮겨도 된다는 결정과 파일 인계가 끝났다는 증거 사이에 실제 작업이 남기 때문입니다. [같은 신청을 승인하거나 반려해 보기](#transfer-demo) · [이관 심사와 조회 SQL](/writing/docuon-transfer-review/)

포털의 이관 대상 목록을 점검하면서 표시상의 차이도 확인했습니다. 조회 SQL은 **심사 상태와 완료일을 따로** 반환하지만, Vue의 목록 변환 함수는 고정된 문자열로 완료 여부를 판정합니다. 원본 함수에 접수·승인·진행·완료·실패·반려를 가정한 여섯 행을 넣자 모두 ‘완료 Y’로 표시됐고, 완료일을 비운 다섯 행의 날짜는 그대로 비어 있었습니다. 가상 입력으로 확인한 화면 동작입니다. 이 열만 보고 수취 보관소에 파일이 도착했다고 판단하기는 어렵습니다.

## 사진 이름으로 찾은 문서의 정산 용량

[가상 문서 세 건에서 파일명으로 정산 조회하기](#billing-workbench)

운영자가 정산 화면에서 ‘현장 사진’을 검색해도 점검표 PDF의 용량까지 나와야 합니다. 파일명 조건에 맞는 행만 먼저 남기고 합산하면 사진 용량만 잡힙니다. 첨부를 모두 펼친 뒤 페이지를 나누면 같은 문서가 여러 줄을 차지합니다.

MyBatis 조회는 보존기한과 등록일 범위에 맞고 검색어를 포함한 첨부가 있는 **문서 ID를 먼저 고른 뒤**, 현재 페이지의 문서에 속한 첨부 전체를 다시 모읍니다. PDF가 1 MiB, 사진이 256 KiB인 예시에서는 검색 결과가 문서 한 줄이고 용량은 1.25 MiB입니다. 화면 열 제목은 ‘용량(Mb)’이며 실제 쿼리는 바이트를 1,048,576으로 나눕니다.

사용자 포털의 월별 등록 통계도 문서 ID로 중복을 제거해 건수를 세고, 용량은 첨부별로 합합니다. 같은 문서를 보더라도 증명서 발급 통계의 단위는 발급 한 건입니다. 최초 등록용 증명서와 폐기된 증명서는 빼고, 선택한 사용자가 해당 기간에 발급받은 결과를 유형별로 셉니다.

## 보존기간 연장과 폐기 후 확인할 기록

보존기간을 6개월 늘릴 때 포털은 문서 ID와 추가 기간을 보냅니다. Java 서비스가 보관 시스템의 응답 본문에서 처리 결과까지 확인하면 포털이 상세를 다시 조회해 반영된 만료일을 표시합니다.

단건 폐기에서는 담당자가 서명할 때 **폐기 전에 원본을 발급받을지** 선택합니다. 원본 발급을 선택했는데 실패했다면, 서비스는 대기 이력에 실패를 기록하고 폐기 요청 전에 멈춥니다. CSV 일괄 폐기는 업로드 직후 대기 목록 등록까지만 확인할 수 있습니다. 파일에 이미 신청된 문서가 있으면 새 대기 건을 등록하기 전에 중복 오류를 반환하고, 접수된 건은 스케줄러가 활성화됐을 때 별도로 처리합니다. 운영자는 콘솔에서 각 문서의 대기·성공·실패를 확인합니다.

사용자 포털에는 기업 구성원·문서 유형 관리가, 운영자 콘솔에는 발급 정책·심사·감사 이력·통계 관리가 함께 있습니다. 등록 화면에서 페이지를 넘겨 11번째 첨부를 삭제할 때 표시 목록과 실제 전송 파일이 일치하는지 확인한 사례는 별도 기술 글에 담았습니다. [첨부 삭제 뒤 전송할 파일 확인하기](/writing/docuon-registration/#attachment-review)

## 탈퇴 신청이 문서 한 건에서 실패했을 때

계정 상태와 대상 문서를 함께 변경하는 도중 문서 B에서 런타임 예외가 발생하면, 앞에서 처리한 문서 A까지 신청 전 상태로 돌아갑니다. 현재 처리 중이던 B의 실패 사유는 다른 Spring 빈이 새 트랜잭션에서 기록합니다. 로컬 실험에서는 계정 상태, 폐기 대기 문서 수, 남은 실패 이력을 호출이 끝난 뒤 다시 조회해 두 커밋의 차이를 확인했습니다. [문서 B의 실패 이력이 남는 이유](/writing/notes-withdrawal-failure-history/)
