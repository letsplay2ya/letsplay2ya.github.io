## 참고 계약에서 상품만 복사하기

이전 계약의 상품을 가져와 새 보험기간으로 견적을 작성하는 상황입니다. 인수 담당자는 두 계약을 나란히 열고 참고 계약에서 상품 한 칸을 선택합니다. 이때 현재 계약에는 **상품코드와 상품명이 함께** 들어가야 합니다. 화면에 새 상품명이 떠도 코드에 이전 값이 남으면, 요율을 조회할 때 다른 상품의 조건이 전달될 수 있습니다.

제가 담당한 범위는 접수, 계약 검토, 요율산정과 운영 화면을 잇는 프론트엔드 전반입니다. 계약 기본정보에서는 선택한 필드마다 함께 옮길 값을 정했습니다. 상품을 선택하면 국내·해외 구분도 따라옵니다. 보험개시일과 종료일은 개별 선택 항목이므로 상품만 복사하면 두 날짜는 유지됩니다. 소급담보일을 선택하면 그 날짜에 붙인 참고내용도 같이 옮깁니다.

이 페이지의 가상 계약에서는 상품코드와 상품명을 한 번에 바꾸고, 선택하지 않은 보험기간과 검토 메모가 그대로 남는 것을 확인할 수 있습니다. 예제에서는 개시일과 종료일을 보험기간 한 묶음으로 선택합니다. [선택 복사 화면](#workspace-title) · [필드별 복사 규칙](/writing/notes-reference-copy/) · [작업 중인 계약을 오갈 때의 상태 복원](/writing/notes-workspace-state/)

## 서류에서 읽은 값을 고친 뒤 AI를 다시 실행하는 시점

이번 계약의 보험기간은 접수 서류에서도 확인할 수 있습니다. OCR 추출 항목을 선택하면 근거가 있는 문서와 페이지가 열리고, 여러 근거가 있으면 다음 위치로 이동합니다. React는 현재 문서의 좌표를 뷰어에 표시할 백분율로 바꿉니다. 이 조회 경로에서는 Java가 이미지 폭과 높이를 빈 값으로 반환하므로 1653 × 2339 기준 크기를 사용합니다. [페이지와 좌표를 연결하는 방법](/writing/notes-document-evidence/)

담당자가 추출된 텍스트를 고치고 확인하면, 포털은 편집한 항목 목록을 Java 서비스에 보냅니다. 서비스는 현재 값을 직전본으로 옮기고 새 목록을 기록한 뒤, 두 세대에서 **내용이 바뀐 항목명**을 골라 재처리 계획을 요청합니다. 그래서 다음 창에서 ‘재추론’을 취소해도 사람이 고친 값은 남습니다. 실행에 동의하면 서버가 변경 목록을 다시 읽어 작업을 요청하고, 화면은 처리 현황으로 이동합니다. 작업 요청을 접수한 시점과 새 추론 결과를 계약에 반영한 시점도 구분됩니다.

접수 정보 자체를 고치면 다른 규칙이 적용됩니다. 파일 유형을 바꿀 때는 추론 대상에 RQ 문서가 정확히 하나인지, 해당 종목에 필요한 설문지가 포함됐는지 검사합니다. 세부종목을 바꾸면 새 분류를 먼저 저장합니다. 재추론을 취소하거나 실행할 작업이 없으면 새 분류를 유지하고, 계획 조회가 실패하거나 실행 요청에서 오류가 나면 이전 분류 복구를 시도합니다. 운영자는 처리 타임라인을 보고 OCR 재처리, AI 작업 재실행, 기존 결과 재반영 중 필요한 단계를 고릅니다. 접수 담당자 배정과 권한·메뉴·처리 로그도 운영 화면에서 관리합니다.

## 담보와 약관으로 보험료 후보 만들기

임원배상책임보험에서는 재무제표의 최근 연도 자산이 해당 목적물의 기본요율을 구하는 입력이 됩니다. 계약상세에서 자산을 고치면 같은 연도 자본을 다시 계산하고 요율 탭으로 자산을 넘깁니다. 약관도 두 단계로 반영합니다. 계약에 적용한 약관 가운데 적용 레벨과 할인·할증 조건을 충족한 항목이 요율 목록으로 넘어갑니다. 그중 비교 대상으로 선택한 약관은 견적에 넣었을 때와 뺐을 때를 각각 계산합니다. [약관의 적용과 할인·할증 대상 판정](/writing/notes-clause-eligibility/)

가상 견적에 일반 담보와 추가 담보 X가 하나씩 있고, 비교할 약관도 하나 있다고 해 보겠습니다. **보상한도**는 해당 담보에서 보상하는 금액의 상한이고, **자기부담금**은 피보험자가 부담하는 금액입니다. 둘의 담보가 일치해야 한 가지 견적 조건이 성립합니다.

| 보상한도와 자기부담금 | 약관 비교 | 계산할 후보 |
| --- | --- | ---: |
| 일반 한도와 일반 부담금 | 포함·제외 | 2건 |
| X 한도와 X 부담금 | 포함·제외 | 2건 |
| 일반 한도와 X 부담금 또는 그 반대 | 짝이 맞지 않아 계산에서 제외 | 0건 |

React는 성립한 네 조합에 각각 계수를 붙이고, Java 연동 서비스는 이 요청을 외부 요율 서비스 형식으로 변환합니다. 응답의 기준보험료를 원래 조건 행에 연결한 뒤 인수 심사 조정 계수와 재보험 수수료를 반영해 제시보험료를 구합니다. 자기부담금 목록 전체를 비울 때는 일반 한도만 ‘부담금 없음’으로 두 건이 남습니다. 반면 다른 추가 담보 Y의 부담금만 입력하면 유효한 조합이 없어 계산을 멈춥니다.

## 표에 두 줄을 보여주면서 견적 네 건을 저장하기

네 후보를 계산한 뒤 X 한도를 고르면 표에는 X 부담금과 짝이 맞는 두 줄이 남습니다. 조건을 바꿔 볼 때마다 다시 계산할 필요는 없습니다. 하단 합계는 선택한 한도·부담금에 맞는 행을 통화별로 더합니다. 위 예시에서 약관 포함·제외 두 행이 남았다면 둘 다 그 통화의 합계에 들어갑니다.

저장을 누르면 편집 중인 그리드 셀부터 확정합니다. 기준보험료와 제시보험료 후보 전체를 목적물 일련번호로 찾아 해당 위험에 합칩니다. 탭 순서를 바꿔도 결과가 같은 목적물로 돌아가며, 일련번호가 중복되거나 맞는 목적물을 찾지 못하면 서버에 보내기 전에 멈춥니다. [목적물 순서가 달라지는 저장 사례](/writing/notes-stable-identity-save/) · [저장 직전 편집 중인 셀의 처리](/writing/notes-commit-before-save/)

Spring 서비스는 기본정보·담보·약관이 같은 계약에 속하는지 확인하고 최신 계약 행을 잠급니다. 저장 가능한 업무 상태이면 상품별 변환기가 담보와 산정 결과를 저장할 행으로 바꿉니다. 기본 스냅샷 방식에서는 기존 행을 같은 변경 번호의 이력으로 남기고 요청 전체로 새 최신본을 구성합니다. 이력 기록, 새 행 삽입, 결과 재조회가 한 트랜잭션이기 때문에 약관 삽입 중 DB 오류가 발생하면 앞서 쓴 기본정보와 담보도 함께 롤백됩니다. ## 전송 버튼을 누른 계약이 외부로 넘어가는 조건

전송을 확인한 직후에 끝나는 작업은 **내부 계약 저장**입니다. 커밋 후 서버가 세부종목과 상품별 변경 내역을 검사해 재추론이 필요한지 판단합니다. React는 그 응답을 먼저 처리합니다.

| 저장 직후의 상황 | 같은 클릭에서 이어지는 일 |
| --- | --- |
| 재추론이 필요하지 않음 | 외부 인수 시스템 전송을 요청합니다. |
| 재추론 대상 작업이 없거나 담당자가 실행을 취소 | 저장 안내를 띄우고 현재 화면에 남습니다. |
| 담당자가 재추론에 동의 | AI 작업을 요청합니다. 접수되면 처리 현황으로 이동하고, 이번 클릭에서 외부 전송 요청은 보내지 않습니다. |
| 서버가 변경 감지 또는 재추론 계획에서 예외를 반환 | 저장은 이미 끝났습니다. 작업 계획이 비어 있으면 화면에는 저장 안내가 표시됩니다. |

외부 전송 경로에 들어가면 Java가 해당 계약의 전송 상태를 선점하고 DB에서 최신 계약을 다시 읽습니다. 임원배상에서는 목적물 상세를 먼저 보내고, 외부 시스템이 돌려준 목적물·담보·위험 번호를 후속 요율 데이터에 연결합니다. 요청이 어디까지 성공했는지가 중요한 이유입니다.

예를 들어 원본 Java 테스트는 **세 번째 목적물의 요율 전송**에서 실패하도록 외부 응답을 대체합니다. 결과에는 이미 끝난 계약기본·상세·약관·위험평가와, 오류가 난 목적물 및 단계가 따로 남습니다. 외부 호출 전 최신 계약을 읽는 데 실패하면 이전 업무 상태 복구를 시도합니다. 반면 상대 시스템이 이미 일부 데이터를 받았을 수 있는 전송 오류, 혹은 전송은 성공했지만 내부 완료 기록이 실패한 경우에는 오류 상태로 변경을 시도합니다.

이 글의 보험 조건과 화면은 가상 사례입니다. 담보 조합은 원본 함수로, 저장 뒤 화면 분기와 OCR 변경 조회는 가상 입력으로 확인했습니다. OCR 수정값 저장과 외부 전송에 관한 원본 Java 테스트 25건은 가상 응답과 모의 데이터 접근으로 검증했습니다.
