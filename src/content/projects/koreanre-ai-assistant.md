인수 담당자가 접수된 계약 한 건을 열면 가장 먼저 서류에서 읽어 낸 값이 맞는지 확인합니다. 마지막에 남겨야 할 것은 어떤 담보와 약관을 전제로 계산했는지 다시 확인할 수 있는 견적입니다. 저는 이 두 시점을 잇는 접수·계약 검토·요율산정 화면과 운영 화면의 프론트엔드를 담당했습니다.

## 접수부터 외부 전송까지 누가 무엇을 처리하나

| 업무 | 사용자가 하는 일 | 서버에서 이어지는 처리 |
| --- | --- | --- |
| 접수·배정 | 접수 목록에서 서류와 담당자를 확인하고 추출값을 원문과 대조합니다. | 접수·담당자 정보를 조회하고, 문서 유형이나 상품 분류가 바뀌면 해당 건의 재처리 계획과 실행을 요청합니다. |
| 인수 심사 | 유사 계약을 찾아 필요한 값만 가져오고, 현재 계약의 목적물·담보·약관을 편집합니다. | 기본정보·상품별 담보·약관을 계약 단위로 조회합니다. 상품·약관·통화 등의 기준정보를 편집 화면에 제공합니다. |
| 요율·계약 확정 | 보상 조건을 바꿔 견적을 비교하고 저장·전송을 결정합니다. | Java 연동 서비스가 상품별 계산 요청을 외부 요율 서비스 형식에 맞춰 보냅니다. 확정할 계약은 이력을 보존해 저장한 뒤 별도 요청으로 외부 인수 시스템에 전송합니다. |
| 운영 | 운영자가 처리 타임라인에서 멈춘 단계를 확인합니다. | OCR부터 다시 처리하는 요청, AI 작업 재실행, 이미 생성한 결과의 재반영을 구분합니다. 담당자 배정과 사용자·역할·메뉴·처리 로그도 관리합니다. |

## 접수에서 문서 유형을 고친 경우와 세부종목을 고친 경우

한 접수에 RQ 문서와 설문지가 들어왔는데 둘 다 RQ로 지정됐다고 해보겠습니다. 담당자가 ‘AI 재추론’을 눌러도 분석은 시작되지 않습니다. 화면은 추론 대상으로 표시한 파일만 세어 RQ가 정확히 하나인지, 각 파일에 문서 유형이 있는지 확인합니다. 설문지를 필수로 받는 종목군에서는 선택한 파일 중 적어도 하나가 설문지여야 합니다. 두 번째 파일의 유형을 바로잡으면 서버가 파일별 문서 유형과 추론 대상 여부를 먼저 저장하고, 작업 서버에 해당 접수의 OCR 재처리를 요청합니다. 요청을 받아들이면 담당자는 접수처리현황으로 이동합니다. OCR이나 AI 추론이 진행 중일 때는 이 건의 심사를 시작할 수 없습니다.

세부종목을 바꿀 때는 이미 만들어진 계약 정보가 걸려 있습니다. 화면은 현재 기본정보를 읽어 둔 뒤 새 종목을 먼저 저장하고, 서버에 재추론 계획을 요청합니다. **담당자가 확인창에서 취소한 경우와 서버가 실행에 실패한 경우에는 남아야 할 종목이 다릅니다.**

| 서버 응답 또는 담당자의 선택 | 화면이 처리하는 방식 |
| --- | --- |
| 계획 조회에 실패했거나 서버가 재추론 불가로 응답 | 변경 전 기본정보를 다시 저장해 이전 종목을 복구하려고 합니다. |
| 재추론이 필요하다는 응답이지만 실행할 작업 목록은 비어 있음 | 새 종목을 유지하고 저장 완료를 알립니다. |
| 실행 여부를 묻는 창에서 담당자가 취소 | 새 종목을 유지한 채 접수 상세에 머뭅니다. |
| 담당자가 동의했으나 실행 요청에 실패 | 오류를 알리고 이전 기본정보 복구를 시도합니다. 복구 요청까지 실패하면 그 사실도 따로 알립니다. |
| 실행 요청에 성공 | 해당 건을 열린 작업에서 빼고 접수처리현황으로 이동합니다. |

## 이번 계약의 보험기간을 확인하고, 참조계약의 조건을 가져오는 법

담당자가 OCR로 읽은 보험기간을 재확인한다고 해보겠습니다. 원시데이터 화면에서 근거가 있는 항목을 누르면 그 항목의 첫 근거가 속한 문서가 열립니다. 근거가 두 곳이면 ‘다음’으로 두 번째 위치까지 따라갑니다. 서로 다른 PDF의 같은 페이지에 근거가 하나씩 있어도 현재 문서에 속한 영역만 표시합니다. 좌표를 원본 이미지 너비와 높이에 대한 비율로 바꾸기 때문에 확대해도 강조 표시가 원문 문구에 맞춰집니다. [OCR 좌표를 PDF 하이라이트와 연결하기](/writing/notes-document-evidence/)

이번 계약의 기간은 그대로 두고 참조계약의 상품 조건만 가져올 수도 있습니다. 기본 계약 화면에서 상품을 선택해 복사하면 상품코드와 상품명이 함께 바뀌고, 따로 선택할 수 없는 국내·해외 구분도 참조계약 값으로 따라옵니다. 보험개시일과 종료일은 각각 선택하는 항목이어서 이 복사에 들어가지 않습니다. 소급담보일을 선택하면 날짜 옆 참고내용도 같이 옮깁니다. 날짜를 옮기면서 그 날짜에 붙은 설명을 예전 계약 값으로 남기지 않도록 두 값을 묶은 것입니다. ## 임원배상에서 계약상세와 약관이 요율 입력이 되는 지점

의료배상과 임원배상은 같은 ‘계약상세’ 탭을 쓰지만 상품에 따라 편집 화면과 요율 계산 화면이 달라집니다. 임원배상에서는 목적물별로 담보지역, 국내·북미 상장 여부와 재무제표를 검토합니다. 가령 올해 자산을 120, 부채를 40으로 입력하면 같은 단위의 올해 자본은 80으로 갱신됩니다. 작년 자본은 그대로입니다. 표를 정렬해 행의 순서가 바뀌어도 자산·부채 등의 항목 코드와 편집한 연도로 수정할 값을 찾습니다. **최근 연도 자산은 그 목적물의 기본요율을 구하는 입력으로도 전달됩니다.** 그래서 계약상세에서 자산을 고친 뒤 요율 화면에 같은 숫자를 다시 적을 필요가 없습니다.

계약 약관(T&C)에서는 ‘적용’과 ‘선택’이 다른 일을 합니다. 선택을 켜면 적용도 켜지고, 적용을 끄면 선택이 풀립니다. 요율 화면의 약관 할인·할증 목록을 만들 때는 적용 여부 외에도 약관의 적용 레벨과 할인·할증 대상 표시를 봅니다. 대상이 명시적으로 ‘아니오’인 약관은 계약에 적용해도 산정 목록에 들어가지 않습니다. 대상 표시가 비어 있는 예전 데이터는 나머지 조건으로 판단합니다.

임원배상에서는 변경 전후 목록을 약관을 식별하는 두 코드로 대조합니다. 이때 같은 계약의 요율 화면에서 이미 편집한 행이 있으면 그 상태를 가져온 뒤 추가·해제된 약관을 반영합니다. 대상 약관의 ‘선택’만 바꾸면 기존 행에서 해당 표시를 갱신합니다. 이 표시가 다음 기준보험료 계산에서 동일한 한도와 자기부담금에 대해 약관을 포함한 경우와 제외한 경우를 나눌지를 결정합니다. [약관을 적용했는데 왜 할인할증 목록에는 없을까](/writing/notes-clause-eligibility/)

## 임원배상책임보험 한 건에서 기준보험료 네 줄이 나오는 이유

인수 담당자가 한 회사의 임원배상책임보험을 검토한다고 가정해 보겠습니다. 일반 담보 외에 추가 담보 X도 제안하고, 약관 한 건을 넣을 때와 뺄 때의 보험료를 비교하려고 합니다. 견적을 만들려면 먼저 두 금액의 짝을 정해야 합니다. **보상한도**는 담보에서 보상하는 금액의 상한이고, **자기부담금**은 사고가 났을 때 피보험자가 부담할 금액입니다.

화면에서는 목적물의 자산과 통화를 받아 원화 환산액을 구하고, 최소 기초수 조건을 반영해 기본요율과 기본보험료를 차례로 조회합니다. 환산액을 구하지 못하면 이전에 표시한 기본요율과 기본보험료를 비웁니다. 기본요율이 있어야 담보지역, 상장 여부, 위험평가, 손해율, 약관 등의 계수를 반영하는 **기준보험료** 계산으로 넘어갑니다.

### 짝이 맞는 한도와 부담금만 계산한다

일반 한도와 일반 부담금 한 쌍, X 한도와 X 부담금 한 쌍을 입력했습니다. 표는 각 계수에 유효한 가상 값을 넣고 원본 화면의 조합 함수를 실행한 결과입니다.

| 보상한도 | 자기부담금 | 비교할 약관 | 계산 후보 |
| --- | --- | --- | ---: |
| 일반 | 일반 | 포함 / 제외 | 2건 |
| 추가 담보 X | 추가 담보 X | 포함 / 제외 | 2건 |
| 일반 | 추가 담보 X | 담보 불일치 | 0건 |
| 추가 담보 X | 일반 | 담보 불일치 | 0건 |

두 담보에서 약관을 한 번씩 넣고 빼므로 계산 서비스로 보낼 후보는 **네 건**입니다. 항상 적용하는 약관을 하나 더 넣어도 후보 수는 그대로입니다. 그 약관의 계수가 네 건에 공통으로 들어갑니다.

자기부담금 입력을 모두 지우면 결과가 또 달라집니다. 일반 한도에 한해 ‘자기부담금 없음’으로 약관 포함·제외 두 건을 만들고, X 한도는 짝이 없어 빠집니다. 반면 부담금 목록에 다른 추가 담보 Y의 값만 남기면 일반 한도에도 X 한도에도 맞는 짝이 없습니다. 화면은 계산 요청을 멈추고 계수를 확인하라고 안내합니다. **빈 목록은 이 상품에서 유효한 견적이 될 수 있고, 불일치하는 목록은 견적을 만들 수 없습니다.**

## 계산 결과를 어디에 표시하고 무엇을 저장할까

계산 서비스가 기준보험료의 총액·순액과 요율을 반환하면 화면은 응답 순서에 따라 금액을 원래 담보·약관 조합에 붙입니다. 다음 단계인 **제시보험료** 계산에는 금액이 들어온 기준보험료 행과 인수 심사 조정 계수, 재보험 수수료 조건이 필요합니다. 기준보험료가 한 건도 없으면 여기서 멈춥니다.

앞에서 네 건을 계산한 뒤 담당자가 X 한도를 선택하면, 표에는 X의 한도와 부담금이 일치하는 두 건만 남습니다. 이미 받은 결과를 걸러 보여주므로 이 선택을 위해 계산 서비스를 다시 호출할 필요가 없습니다. 하단 합계 역시 목적물마다 선택한 한도와 부담금을 기준으로 계산합니다. 약관 포함·제외 두 행이 모두 이 조건에 맞으면 두 금액이 모두 합계에 들어갑니다. 가상으로 두 행을 USD 100과 USD 120, 다른 목적물에서 선택된 행을 KRW 9,000으로 두었을 때 원본 집계 함수는 **USD 220과 KRW 9,000**을 별도로 반환했습니다.

저장할 때는 선택한 두 줄이 아니라 계산해 둔 후보 전체가 필요합니다. 마지막으로 편집하던 그리드 셀을 먼저 확정하고, 목적물 일련번호를 기준으로 각 위험의 상세 데이터에 기준보험료와 제시보험료 목록을 합칩니다. 탭 순서가 달라져도 같은 목적물에 귀속됩니다. 일련번호가 중복되거나 대응하는 목적물을 찾지 못하면 통합 저장 요청을 보내기 전에 중단합니다. Java 저장 변환기는 위험별로 받은 두 목록에서 각각 저장할 결과 행을 구성합니다. [목적물 순서가 바뀐 경우의 저장](/writing/notes-stable-identity-save/) · [마지막 입력을 확정하는 순서](/writing/notes-commit-before-save/)

## 약관을 한 건 빼고 저장하면 이전 견적은 어떻게 남을까

인수 담당자가 견적에서 약관 하나를 빼고 다시 저장한다고 해 보겠습니다. React 화면은 계약 기본정보, 목적물별 담보와 보험료 후보, 편집을 마친 약관 목록을 한 요청에 담습니다. Spring 서비스는 세 부분이 같은 계약에 속하는지 확인하고 데이터베이스의 최신 계약 행을 잠급니다. 그사이 업무 단계가 바뀌어 저장할 수 없는 상태라면 일반 모드에서는 기존 기록을 수정하기 전에 충돌 응답을 돌려줍니다. 저장할 수 있을 때도 업무 상태는 서버가 잠금 시점에 읽은 값을 새 최신본에 이어 씁니다.

계약 기본정보와 약관을 저장하는 순서는 상품이 달라도 공유합니다. 담보·요율 부분은 상품별로 입력 구조가 달라, 임원배상 요청은 해당 상품의 Java 구현이 목적물 아래의 위험을 따라가며 기준보험료와 제시보험료를 각각 저장할 행으로 바꿉니다. 기본 스냅샷 방식에서는 이번 저장이 다시 만드는 기존 행들을 같은 변경 번호의 이력으로 먼저 옮기고, 요청에 담긴 기본정보·담보·약관을 새 최신본으로 넣습니다. 약관 목록과 연결된 담보 조건에서 함께 제거한 약관은 이전 견적의 이력에 남고 새 견적에서 빠집니다. 반대로 화면에 보이는 보험료 두 줄만 보내면 나머지 후보도 최신본에서 빠질 수 있습니다. 앞서 네 줄 전체를 보낸 이유입니다.

이력 처리와 새 행 삽입, 기본정보·담보·약관 재조회는 한 트랜잭션 안에서 진행합니다. 마지막 약관을 쓰는 도중 데이터베이스 오류가 나면 앞에서 처리한 기본정보와 담보도 함께 롤백됩니다. 성공하면 서비스가 다시 읽은 계약을 돌려주고 화면은 이번 저장 상태를 다음 초기화의 기준으로 삼습니다. [계약 일부가 빠진 저장 요청의 의미](/writing/notes-full-snapshot-api/)

## 계약을 저장한 뒤 외부 인수 시스템으로 보내는 과정

담당자가 전송을 확인하면 화면은 먼저 현재 편집한 계약을 통합 저장하고, 전송 단계에서는 계약과 상품을 지정합니다. Java 서비스는 전송 가능 상태를 확인한 뒤 계약을 ‘전송 중’으로 바꾸고 데이터베이스에서 최신 견적을 다시 읽습니다. 같은 계약에 대해 먼저 전송이 진행 중이면 두 번째 요청은 막힙니다. 서비스는 저장된 견적에서 목적물별 전송 자료를 만들고 계약 기본정보·상세, 약관, 위험평가, 요율 순으로 외부 시스템에 전달합니다.

실패한 위치에 따라 담당자가 확인해야 할 사실도 달라집니다. 최신 견적을 읽다가 실패하면 외부 저장을 시작하기 전이므로 이전 업무 상태로 복구합니다. 반면 계약 기본정보를 보낸 뒤 약관 전송에서 오류가 났다면 앞선 단계의 데이터가 상대 시스템에 남아 있을 수 있습니다. 이때 서비스는 실패 지점을 남기고 계약을 전송 오류 상태로 변경하려고 합니다. 외부 전송을 모두 마쳤는데 내부의 완료 상태 기록만 실패한 경우에도 별도로 전송 오류 상태 기록을 시도합니다. 같은 ‘전송 실패’라도 어느 시스템에서 마지막으로 성공했는지가 다음 확인 대상을 결정합니다.
