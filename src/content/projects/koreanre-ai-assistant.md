접수한 계약의 정보를 확인하고, 담보와 약관을 검토한 뒤 보험료를 산정하는 업무 시스템입니다. 저는 접수·계약·산정·운영 화면부터 공통 UI, 상태 관리와 API 연동까지 프론트엔드 전 범위를 담당했습니다.

중심 화면은 **계약 기본정보 → 계약 상세정보 → Terms&Conditions → 요율산정**의 네 개 탭으로 구성됩니다. 각 탭의 입력과 조회 결과를 연결하면서, 사용자가 여러 계약을 오가거나 참고 계약을 비교해도 현재 작업의 맥락을 유지하도록 구현했습니다.

## 화면을 읽는 방법

네 탭은 서로 다른 CRUD 화면의 모음이 아니라, 하나의 계약을 검토해 저장 가능한 산정 결과로 만드는 흐름입니다. 각 단계에서 유지해야 하는 데이터의 관계가 다릅니다.

| 업무 단계 | 사용자의 판단 | 구현에서 지키는 관계 | 자세한 근거 |
| --- | --- | --- | --- |
| 접수·원문 검토 | 추출된 값의 근거가 맞는가 | 추출 항목 ↔ 문서·페이지·좌표 | [PDF 근거 연결](/writing/notes-document-evidence/) |
| 기본정보 비교 | 참고 계약의 어떤 값만 가져올까 | 선택 필드 ↔ 코드·표시명 묶음 | [선택 복사](/writing/notes-reference-copy/) |
| 상세정보·약관 편집 | 어느 목적물·약관을 적용할까 | 화면의 행 ↔ 업무 식별자·적용 조건 | [식별자 기반 병합](/writing/notes-stable-identity-save/) |
| 요율 계산 | 이 응답은 지금 조건의 결과인가 | 요청 계약·대상·입력 ↔ 현재 상태 | [응답 적용 조건](/writing/notes-async-calculation/) |
| 저장 준비 | 마지막 입력까지 반영됐는가 | 입력기 초안 → store → 전송 데이터 | [입력 확정 순서](/writing/notes-commit-before-save/) |
| 다른 계약으로 이동 | 돌아오면 어디서 이어갈까 | 여러 store·탭 ↔ 하나의 UW 번호 | [상태 복원](/writing/notes-workspace-state/) |

예를 들어 참고 상품을 복사한 뒤 담보를 수정하고 계산하는 동안 다른 계약을 열 수 있습니다. 이때 상품명만 바뀌거나, 목적물 순서로 저장 대상을 찾거나, 이전 조건의 계산 응답이 반영되면 각 화면이 단독으로는 정상이어도 계약 전체의 값은 맞지 않을 수 있습니다. 아래 탭별 설명은 이런 연결 지점을 기준으로 읽을 수 있습니다.

**Current**는 작업 중인 계약, **Reference**는 비교 대상으로 선택한 계약입니다. AI Assistant가 열린 상태에서는 Current와 유사 UW 추천 패널을 보여주고, 참고 계약을 선택하면 Current와 Reference를 비교하는 구성으로 전환합니다. AI Assistant와 Reference는 같은 시점에 상시 펼쳐 두는 세 번째·두 번째 패널이 아닙니다.

탭 상단의 **AI 요약정보**는 별도 공통 컴포넌트입니다. 기본정보·상세정보·약관·요율 화면에서 각각 전달한 내용을 표시합니다. 우측 AI Assistant의 기본 콘텐츠는 유사 계약 추천이며, 추천 결과 선택과 직접 검색을 통해 비교 대상을 정할 수 있습니다.

페이지 상단은 기본정보 선택 복사에 집중한 실행 예제입니다. 원본 React 공통 UI 세 개를 분리하고 포트폴리오용 상태 연결을 추가했습니다. 전체 React 애플리케이션이나 운영 API를 실행하는 화면은 아닙니다. 네 탭 관계를 보여주던 기존 Vue 예시는 접을 수 있는 보조 영역으로 옮겼습니다. [선택 복사의 원본 근거와 예제 차이](/writing/notes-reference-copy/)에서 구분해 설명합니다.

## 01. 계약 기본정보 — 비교한 내용을 현재 계약에 반영하기

### 문제

계약자·피보험자, 보험기간, 지역, 상품 분류 등 여러 입력이 한 계약에 연결됩니다. 참고 계약을 활용할 때도 사용자가 선택한 값과 현재 계약의 값을 구분하고, 서로 연관된 코드와 표시명을 함께 반영해야 합니다.

### 구현

Current 입력과 Reference 조회 영역을 분리하고, 참고 계약에서 선택한 필드를 현재 계약의 Zustand 상태에 적용하는 매핑을 구성했습니다. 단순히 객체 전체를 덮어쓰지 않고 계약자, 주소, 상품 분류, 기간 등 필드별 적용 규칙을 사용합니다. 보험기간 입력에서는 시작일과 종료일의 선후 관계도 검사합니다.

작업 계약을 전환할 때는 기본정보뿐 아니라 하위 탭과 참고 계약 상태를 스냅샷으로 보관합니다. 재진입 시 저장소 복원을 마친 뒤 탭 콘텐츠를 표시하고, 서버와 동기화된 원본은 깊은 복사로 분리해 초기화 기준을 유지합니다.

### 검증 관점

- Reference에서 일부 항목만 선택했을 때 해당 필드와 연결된 코드·표시명이 함께 반영되는지 확인합니다.
- 보험 시작일이 종료일보다 늦은 입력을 허용하지 않는지 확인합니다.
- 계약 A를 편집한 뒤 B로 이동하고 A로 돌아왔을 때 입력값과 탭 위치가 복원되는지 확인합니다.

### 관련 원본 파일

- `src/pages/uw-main/tabs/DefaultContract/index.tsx` — 선택 필드의 적용과 Current/Reference 구성
- `src/pages/uw-main/tabs/DefaultContract/ContractCurrent.tsx` — 기본정보 입력과 조회
- `src/components/ui/DatePicker/dateRangeValidation.ts` — 기간 선후 관계 검사
- `src/pages/uw-main/useUwSnapshot.ts` — 업무 단위 상태 저장·복원

## 02. 계약 상세정보 — 종목별 담보 구조와 편집 상태 연결하기

### 문제

종목마다 목적물·담보·위험의 구성과 입력 항목이 다릅니다. 배열의 위치와 사용자가 인식하는 업무 대상이 항상 일치하지 않고, 그리드에서 편집 중인 값이 아직 상위 저장 데이터에 반영되지 않은 상태도 고려해야 합니다.

### 구현

상품 코드에 따라 해당 종목의 상세정보 컴포넌트를 선택하고, 종목별 조회 데이터를 화면과 저장 형식에 맞춰 정규화했습니다. 예를 들어 임원배상(D&O) 상세 화면은 저장이나 탭 이탈 전에 현재 입력을 반영하는 함수를 등록합니다. 저장용 데이터에서는 화면 전용 식별자와 표시 필드를 제거합니다.

비교 화면에서는 동일 업무 구역에 부여한 키로 Current와 Reference의 그리드를 연결합니다. 너비가 달라도 같은 진행률로 가로 스크롤을 맞추고, AG Grid가 내부 요소를 다시 생성하면 새 요소에 이벤트를 연결하도록 처리했습니다.

### 검증 관점

기존 `dnoPayload.test.ts`에는 신규 담보의 기본값, 통화 초기화, 저장 전 UI 전용 필드 제거를 확인하는 테스트가 있습니다. `syncedScroll.test.tsx`에는 DOM 순서와 너비가 다른 그리드를 같은 키로 연결하고 양방향으로 동기화하는 사례가 있습니다.

화면에서는 마지막으로 편집한 셀을 유지한 채 탭을 바꾸거나 저장했을 때 값이 빠지지 않는지, 참고 계약의 선택 항목이 대응하는 현재 영역에 반영되는지를 확인 대상으로 삼았습니다.

### 관련 원본 파일

- `src/pages/uw-main/index.tsx` — 종목별 상세·요율 컴포넌트 선택과 통합 저장
- `src/pages/uw-main/tabs/DetailContract/DetailDNO/index.tsx` — 입력 반영 시점과 비교 영역
- `src/pages/uw-main/tabs/DetailContract/DetailDNO/dnoPayload.ts` — 저장 데이터 정규화

## 03. Terms&Conditions — 약관 선택·순서·적용 상태 관리하기

### 문제

증권과 약관은 목록의 순서, 적용 여부, 설명, 참고 계약과의 중복 여부를 함께 다뤄야 합니다. 약관 변경은 관련 할인·할증 정보에도 영향을 주므로 화면에 보이는 행과 산정에 쓰는 데이터를 연결할 필요가 있습니다.

### 구현

증권별 약관 묶음을 구성하고 조회 순서와 코드를 기준으로 정렬했습니다. 계약의 국내·해외 구분에 따라 지역 탭을 노출하고, 적용 여부 변경, 순서 조정, 설명 편집과 참고 약관 복사를 연결했습니다.

참고 약관 선택 복사에서는 기존 항목과의 중복을 확인합니다. 일괄 교체는 기존 증권·약관이 교체되는 동작을 확인받은 뒤 수행합니다. 변경 전후 약관을 비교해 관련 파생 항목을 갱신하며, 적용 여부와 할인·할증 대상 여부를 별도 조건으로 판단합니다.

### 검증 관점

- 선택한 참고 약관에 기존 항목이 포함되면 중복을 안내하고, 같은 항목이 반복 추가되지 않는지 확인합니다.
- 일괄 교체를 취소했을 때 현재 약관이 유지되는지 확인합니다.
- 적용 여부 변경과 약관 추가·삭제 후 연결된 할인·할증 항목이 함께 갱신되는지 확인합니다.
- 지역 탭 표시, 정렬과 설명이 해당 계약의 데이터에 맞는지 확인합니다.

### 관련 원본 파일

- `src/pages/uw-main/tabs/TermnCondition/index.tsx` — 증권·약관 편집, 복사와 변경 반영
- `src/pages/uw-main/tabs/TermnCondition/termConditionSort.ts` — 약관 정렬 기준
- `src/pages/uw-main/tabs/TermnCondition/termClauseEligibility.ts` — 파생 할인·할증 대상 판정
- `src/pages/uw-main/tabs/TermnCondition/OverseasTermnCondition.tsx` — 해외 약관 화면

## 04. 요율산정 — 현재 조건에 맞는 결과를 저장하기

### 문제

기준보험료와 할인·할증 등을 계산하는 동안 사용자는 입력을 수정하거나 다른 계약·목적물로 이동할 수 있습니다. 계산 성공 여부와 별개로 응답이 현재 입력에 유효한지 확인해야 하며, 탭별 편집 상태를 저장 형식에 맞게 합치는 과정도 필요합니다.

### 구현

자동계산 요청에 계약 번호, 대상 키, 입력값 서명과 화면 수명을 기록하고, 응답을 반영하기 직전에 최신 상태와 대조하는 공통 훅을 구성했습니다. 화면이 해제되거나 계약·대상·입력이 달라지면 이전 조건의 결과를 적용하지 않습니다.

임원배상 요율 화면에서는 그리드와 지연 반영 입력을 확정한 뒤 탭별 산정 상태를 상세 저장 데이터에 합칩니다. 목적물 식별자로 대상을 맞추고 기존 서버 식별자를 보존하며, 검증 오류가 있으면 저장을 진행하지 않도록 연결했습니다. Current와 Reference의 대응 구역 높이와 가로 탐색도 함께 조정합니다.

### 검증 관점

기존 `medicalAutoCalculation.test.ts`는 숫자 표기의 정규화와 실제 입력 변경이 요청 서명에 미치는 영향을 다룹니다. `dnoRateSave.test.ts`와 `useRateDnoStore.test.ts`에는 목적물 순서가 달라진 경우의 편집값 병합·이동, 기존 서버 식별자 보존에 관한 테스트가 있습니다.

응답 보호의 범위는 상태 반영 여부입니다. 네트워크 요청 취소나 동일 입력으로 보낸 중복 요청의 응답 순서를 보장하는 기능까지 포함하지 않습니다.

### 관련 원본 파일

- `src/pages/uw-main/tabs/RateCalculation/utils/useAutoCalculationGuard.ts` — 응답 적용 조건
- `src/pages/uw-main/tabs/RateCalculation/RateCSA/ContractCurrent.tsx` — 최신 대상·입력과 대조하는 실제 계산 흐름
- `src/pages/uw-main/tabs/RateCalculation/RateDNO/index.tsx` — 입력 확정과 저장 전 병합
- `src/pages/uw-main/tabs/RateCalculation/RateDNO/dnoRateSave.ts` — 식별자 기반 저장 형식 변환
- `src/pages/uw-main/tabs/RateCalculation/RateDNO/dnoRateSave.test.ts` — 병합·식별자 보존의 기존 테스트

## 네 개 탭 밖에서 연결한 업무

접수 현황 검색과 파일·메일 확인, OCR 원문 검토, 워커 처리 현황과 타임라인, 사용자·역할·메뉴·로그·배정 관리 화면도 구현했습니다. 공통 UI와 그리드·팝업, 세션·접근 권한 처리, API 요청·로딩 상태를 업무 화면에 연결했습니다.

OCR 검토 화면은 항목의 문서 ID·페이지·좌표를 PDF 뷰어와 연결합니다. 사용자가 추출값의 근거를 선택하면 해당 위치를 표시하고, 한 항목에 연결된 여러 근거를 순서대로 확인할 수 있습니다.

## 설명과 검증의 범위

이 글은 프로젝트 코드와 기존 테스트 소스를 바탕으로 구현을 설명합니다. 위 검증 항목은 확인 시나리오와 기존 테스트의 대상이며, 이 문서를 작성하면서 운영 시스템의 통합 테스트를 실행했다는 의미는 아닙니다.

계약별 상태 복원은 실행 중인 앱의 화면 전환을 대상으로 합니다. 브라우저 새로고침 이후까지 작업 스냅샷을 보관하지 않습니다. AI·OCR 관련 기여는 결과 검토 화면과 API 연동이며 모델 학습이나 인식 정확도 개선을 이 프로젝트의 기여로 기재하지 않았습니다. 개발 기간, 팀 규모와 측정하지 않은 운영 개선 수치도 포함하지 않았습니다.
