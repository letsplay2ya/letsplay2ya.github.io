# 블로그와 포트폴리오 발전 방향

검토일: 2026-10-16. 이 문서는 최초 방향 제안이다. 이후 요청으로 적용한 내용과 남은 검증 범위는 [발전 방향 적용 결과](./DEVELOPMENT-2026-10-16.md)에 별도로 기록한다.

## 현재 결과물의 한계

10월 15일에는 6편의 오류를 수정하고 설명용 예제를 검증했다. 정확성 개선의 가치는 있지만, 그것만으로 글이 차별화되지는 않는다. 글마다 정의·예제·주의점이 비슷하게 반복되고, 개인이 겪은 맥락과 판단 근거가 부족하다. 홈페이지를 간소화한 뒤에도 소개 페이지에는 추상적인 표어가 남아 있다. 코리안리의 설명용 화면 역시 실제 상품별 업무 화면을 충분히 보여주는 증거가 아니다.

완료 기준을 빌드·링크·코드 예제 실행에서 끝내지 않는다. 독자가 무엇을 새롭게 이해하는지, 프로젝트 경험을 무엇으로 확인할 수 있는지까지 검토한다.

## 남은 10편의 처리 제안

| 현재 원고 | 제안 | 독자에게 남길 내용 |
| --- | --- | --- |
| Oracle 설치·접속·SQL Developer 3편 | 하나의 실습 환경 안내로 통합 검토 | 서버·클라이언트·서비스 이름·사용자·권한의 구분. 설치 버전과 재현 환경 명시 |
| Oracle CSV 적재 1편 | 우선 개정 | 원본 CSV → 문자열 스테이징 → 명시적 형식 변환 → 실패 행 분리 → 건수·중복 검증 |
| Oracle Python 연동 1편 | 재현 실험 후 개정 | 실제 DSN 사용, 연결·커서 수명, 바인드 변수, 트랜잭션, 분할 조회. 최신 드라이버 선택은 대상 환경과 맞춰 확인 |
| Git/Hexo·Docker/Hexo 2편 | 설치 나열을 배포 구조·환경 재현 주제로 전환 | 원고·빌드 산출물·호스팅 구분. Docker가 필요한 조건과 불필요한 조건 |
| NumPy 기초 1편 | 좁은 문제로 재집필 | 뷰와 복사, 원본 배열 변경, shape·axis. empty와 난수 생성의 혼동 수정 |
| Plotly 게시·그래프 임베드 2편 | 하나의 재현 가능한 시각화 사례로 통합 검토 | 데이터·실행 코드·차트 해석·HTML 배포. 외부 계정 없이 재현하는 방법과 번들 크기의 선택 |

통합은 원고를 삭제하거나 기존 URL을 무효화한다는 뜻이 아니다. 대표 글과 과거 기록의 관계를 먼저 정한 뒤 이전 주소·링크를 유지한다. 아직 통합과 아카이브 분리는 구현하지 않았다.

### 확인된 구체적 문제

- `legacy-oracle-ch1`: 내부 설정과 DBA 권한 부여를 전제로 계정을 생성한다. PDB 로컬 사용자와 필요한 권한을 먼저 설명하는 구조로 재검토한다.
- `legacy-oracle-ch3`: DATE/NUMBER 적재 실패를 전부 VARCHAR2로 바꾸는 것으로 끝낸다. 원인 진단과 적재 이후의 타입 정규화가 없다.
- `legacy-oracle-ch4`: DSN을 생성하고 연결 호출에는 전달하지 않는다. 전체 fetchall 및 to_sql replace가 데이터 규모·기존 테이블에 미치는 영향도 설명하지 않는다.
- `legacy-numpy`: empty를 무작위 값으로 채우는 함수로 설명한다. 초기화되지 않은 메모리와 난수 생성을 구분해야 한다.
- `legacy-setup-docker-hexo`: 움직이는 lts 태그, 빌드 중 의존성 설치, 개발 서버·배포·소스 동기화가 혼재한다.
- `legacy-plotly-01`: 그래프만 있고 데이터·질문·해석이 없다.

## 사이트의 중심

정체성은 'Java와 React/Vue를 사용해 업무 시스템을 개발한 사람의 기록'으로 잡는다. 프레임워크 이름을 폭넓게 나열하기보다 업무 문제, 데이터의 이동, 화면과 서버 사이의 경계를 보여준다. WebSquare/eXBuilder 전환 분석과 AI Agent는 실제 확보한 근거의 수준에 맞춰 확장한다.

홈에서는 대표 글 3편을 직접 선정해 먼저 보여주고 최근 글은 별도로 둔다. 단순 설치·학습 기록은 접근 가능하게 유지하되 대표 사례와 같은 무게로 전시하지 않는 방안을 검토한다. 이 선택 기준은 글의 난이도가 아니라 설명과 재현의 완성도다.

## 대표 콘텐츠 후보

1. **코리안리의 계약 전환과 편집 상태 복원**: 어떤 업무 흐름에서 문제가 생기는지, 원본 상태 구조, 전환 순서, 대안, 재현 테스트를 연결한다.
2. **저장 후에도 같은 데이터를 가리키는 화면 만들기**: 정렬·탭 전환·서버 식별자 병합을 하나의 사례로 묶는다. 기존 글의 중복을 줄인다.
3. **CSV 적재 성공과 데이터 정합성은 다른 문제다**: 날짜·숫자·빈 값이 섞인 소규모 공개 샘플을 만들고 실패 행과 건수 검증을 재현한다.

이들은 작성 후보이며 실제 장애 경험이나 미측정 개선 수치를 뜻하지 않는다. 업무 소스로 구조를 확인할 수 있는 사실과 본인의 결정·실제 효과를 구분한다.

## 프로젝트 상세의 보강 방향

화면 탭마다 '화면 → 사용자가 하는 일 → 구현의 어려움 → 코드와 검증'을 연결한다. 원본 캡처를 사용할 수 있다면 공개 가능한 정보로 정리한다. 캡처를 확보할 수 없다면 원본 컴포넌트를 검토해 가상 데이터로 독립 실행하는 방안을 우선 평가한다. 설명용 재구성을 원본 스크린샷처럼 제시하지 않는다.

모든 탭을 얕게 흉내 내기보다 기본정보 비교·원문 근거 확인·요율 응답 제어 중 근거가 충분한 화면을 먼저 완성한다. 기본정보와 요율 표의 색상만 맞추는 수준은 완료 기준이 아니다.

## AI Agent 확장

입문 개념을 여러 편 생성하기보다 작은 도구 하나를 실제로 만들어 실행 기록을 남긴다. 후보는 공개 예제 저장소의 문서·코드 불일치를 찾는 읽기 전용 도구다. 정답이 있는 샘플, 잘못된 탐지, 도구 호출 실패, 실행 시간과 비용을 함께 기록한다. 구현 전에는 완료된 프로젝트나 개인 실적으로 표시하지 않는다.

## 작업 순서와 완료 기준

1. Oracle 계정·적재·NumPy 글에서 명확한 오해를 먼저 수정한다.
2. CSV 대표 글 한 편을 데이터와 실행 결과까지 완성해 글의 기준으로 삼는다.
3. 코리안리 대표 기능 하나를 실제 화면 근거와 코드·재현 테스트로 깊게 설명한다.
4. 대표 글·최근 글·과거 학습 기록의 탐색 구조를 조정하고 소개 페이지의 추상 문구를 정리한다.
5. 나머지 원고를 통합·개정하고 이후 AI Agent 실험을 추가한다.

각 글은 하나의 질문에 답해야 한다. 실패 입력과 실제 출력, 선택하지 않은 대안과 이유, 적용 범위, 독자가 재현할 최소 파일을 검토한다. 구조는 내용에 맞게 바꾸며 모든 글에 같은 소제목 템플릿을 강요하지 않는다. 코드 테스트와 편집 품질 검토는 별도로 수행한다.
